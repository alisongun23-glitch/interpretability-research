# How language models are trained to write an in-text tool call and read back its answer (Toolformer, GSM8K calculator, ToolkenGPT, Calc-X, chat-template function calling)

Scope note for the report writer: the target system is a 4-layer, d_model 128, 4-head GPT with a 64-token context, trained on TinyStories plus inserted word problems, where every integer 0-255 is a single token and the "tool" is an 8-bit gate-level CPU doing +, - and x. Every finding below is from a primary source (paper section, repo file, or official docs); items marked **[inference]** are my reading, not something a source states. Verbatim strings are in code spans or quotation marks.

## Key question 1: Exactly how is the call written in the text, what stops generation so the tool can run, how is the result inserted, and how does generation resume?

### Takeaway
Four distinct conventions exist: (a) Toolformer's inline bracket call `[Calculator(735 / 499) -> 1.47]`, where the literal `->` is the stop signal and the system inserts the result plus `]`; (b) GSM8K's `<<50*3=150>>`, where the `=` token is the stop signal and the calculator appends `150>>`; (c) ToolkenGPT's dedicated new vocabulary entry per tool (a "toolken" whose id is >= the word-vocab size), whose mere sampling stops generation, after which a separate "tool mode" prompt writes the arguments and only the result is pasted into the text; (d) chat-template function calling, where the call is a whole assistant turn (`<tool_call>{json}</tool_call>` + end-of-turn token) and the result comes back as a separate `tool`-role message rendered by the template before a fresh assistant header. Calc-X (XML-style `<gadget id="calculator">..</gadget><output>..</output>`) is a fifth variant used with small T5 models.

### Cited Findings

**Toolformer (Schick et al., 2023, arXiv 2302.04761)**
- Call format, §2: a call `c = (a_c, i_c)` is linearized as `e(c) = <API> a_c(i_c) </API>` without a result and `e(c, r) = <API> a_c(i_c) → r </API>` with result `r`; "where "<API>", "</API>" and "→" are special tokens." — [Toolformer §2, ar5iv](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Footnote 1 (verbatim): "In practice, we use the token sequences "[", "]" and "->" to represent "<API>", "</API>" and "→", respectively. This enables our approach to work without modifying the existing LM's vocabulary." (The ar5iv rendering shows a leading space, `" ["`, which may be a typesetting artifact.) — [Toolformer fn.1](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Stop/insert/resume, §2 "Model Finetuning"/inference paragraph (verbatim): "When generating text with M after finetuning with our approach, we perform regular decoding until M produces the "→" token, indicating that it next expects the response for an API call. At this point, we interrupt the decoding process, call the appropriate API to get a response, and continue the decoding process after inserting both the response and the </API> token." — [Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Concrete calculator examples from Table 10 (verbatim text with the rendered special tokens): "<API> Calculator(735 / 499) → 1.47 </API> 1.47 (735 / 499) times hotter than it should be." and "<API> Calculator(85 / 23) → 3.70 </API> 65% had a cardiac aetiology". — [Toolformer Table 10](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Calculator tool, §3: "we only support the four basic arithmetic operations." and "Results are always rounded to two decimal places." — [Toolformer §3](https://ar5iv.labs.arxiv.org/html/2302.04761)
- The reference re-implementation's README uses the same bracket/arrow surface form in its mock example, `[inc(1) → 2] and [dec(2) → 1] and [ignored(3)]`, uses two reserved ids `mock_api_start_id = 19998` and `mock_api_stop_id = 19999` for the start/stop tokens, and lists as a todo: "api token (which was left and right brackets in paper) needs to be customizable". — [lucidrains/toolformer-pytorch README](https://github.com/lucidrains/toolformer-pytorch)

**GSM8K calculator annotations (Cobbe et al., 2021, arXiv 2110.14168; openai/grade-school-math)**
- Format in the data (verbatim training-solution line from the repo README): "The booth made $50 x 3 = $<<50*3=150>>150 selling cotton candy each day." The README also states: "If you would like to remove the calculator annotations, simply remove any string that starts with `<<` and ends with `>>`." and "the final numeric solution is the final line of the solution, preceded by `####`." — [grade-school-math README](https://github.com/openai/grade-school-math)
- Paper §4 (verbatim): "To mitigate this issue, we train all models to use a calculator by injecting calculation annotations into the training set. At test time, a calculator will override sampling when the model chooses to use these annotations. Details can be found in Appendix C." — [GSM8K §4, ar5iv](https://ar5iv.labs.arxiv.org/html/2110.14168)
- Appendix C (verbatim): "During testing, we override model sampling when a well-formatted annotation exists, specifically overwriting the token(s) directly following "=" and within <<…>>." and "To simulate the calculator, we simply use the python eval function to evaluate the tokens in the expression (Figure 9). Evaluations that time out or throw an error result in the annotations being skipped and the model being sampled from as usual." — [GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)
- The stop signal in code is the `=` token: `calculator.py` generates one token at a time and checks `if out[0, -1].item() in EQUALS_TOKENS:` with `EQUALS_TOKENS = set([28, 796, 47505])` (GPT-2 token ids); if `use_calculator(text)` returns a value it does `text = text + str(answer) + ">>"` and sets `qn = text` so the next loop iteration continues decoding after `>>`. The README says "The core calculator sampling logic can be found in `calculator.py:sample`." — [calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py); [README](https://github.com/openai/grade-school-math)
- `use_calculator` (verbatim logic): returns `None` if `"<<"` is absent, takes the text after the last `<<`, returns `None` if `">>"` already appears or no `"="` is present, takes `lhs = remaining.split("=")[0]`, strips commas, returns `None` if any character is not in `"0123456789*+-/.()"`, else returns `eval_with_timeout(lhs)` (3-second SIGALRM timeout; exceptions return `None`). — [calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py)

**ToolkenGPT (Hao et al., 2023, arXiv 2305.11554; Ber666/ToolkenGPT)**
- Figure 1 caption (verbatim): "Toolken embeddings are appended to the language model head like regular word tokens. In the "reasoning mode" for solving the problem, the LLM generates text as usual, except that any plugged-in toolkens are also considered for the next token generation. Once a toolken is predicted, (1) the LLM switch to the "tool mode", which provides a few demonstrations of the same tool to complete the arguments. Then, (2) the tool call is executed, and (3) the result is sent back to the text to continue the reasoning mode until the final answer is generated." — [ToolkenGPT §3, ar5iv](https://ar5iv.labs.arxiv.org/html/2305.11554)
- §3.1 (verbatim): "the LLM predicts the next token with the probability as follows: P(t_i | t_<i) = softmax([W_ν ; W_τ] · h_{i−1}) (1) where the next token can be either a word token or a toolken, i.e. t_i ∈ V ∪ T". W_τ ∈ R^{|T|×d} is the toolken matrix, W_ν ∈ R^{|V|×d} the LM head. — [ToolkenGPT §3.1](https://ar5iv.labs.arxiv.org/html/2305.11554)
- §3.1 (verbatim): "the LLM switches into the "tool mode" once its toolken is predicted as the next token ... Specifically, the LLM pauses the generation and appends the current generated context to another prompt. The prompt in tool mode consists of in-context demonstrations for the predicted tool, showing how to generate the tool arguments by quoting the tool calls in a special syntax of [tool](arguments). ... Finally, the arguments are sent to the specified tool for execution, and the returned value is sent back to the text in the reasoning mode." — [ToolkenGPT §3.1](https://ar5iv.labs.arxiv.org/html/2305.11554)
- Surface syntax in the arithmetic demonstrations (Appendix A.2): the call is written inline right after the `=`, e.g. `147+354=<add>(147,354)=501`; the reasoning-mode CoT prompt begins "Answer the following questions step by step:" and the ReAct-style tool prompt begins "Answer the following question with <add>, <subtract>, <multiply>, <divide>, <power>, <sqrt>, <log>, ...". — [ToolkenGPT appendix, arXiv HTML](https://arxiv.org/html/2305.11554)
- Code, stop condition: in `FunctionLM.generate` the combined logits are `logits = torch.cat([logits_token, logits_func], dim=-1)` and decoding breaks on `if next_token[0] >= 32000 or next_token[0] in stop_token_single:` — i.e. sampling any toolken (ids 32000+ for LLaMA) ends the reasoning-mode generation. — [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py)
- Code, tool mode and insertion (`func_embedding_inference`): the toolken id is decoded to its name with `decode_token = lambda x: funcmodel.tokenizer.decode(x) if x < 32000 else func_map[x - 32000]`; the loop checks `if cur_generation.endswith(op+"("):`; it then builds `prompt = templates[op].replace("[QUESTION]", question) + cur_generation_with_func`, sets `funcmodel.inference_mode = "baseline"`, and generates arguments with `stop_token=[29897, 3892]`; it calls `res = eval(f"{op[1:-1]}_{args}")`, records `func_calls.append(f"{op}{args} = {res}")`, and replaces the call text by the bare result: `cur_generation = cur_generation.split(op)[0] + str(res)`. Reasoning then resumes with a one-token generation in which digit tokens are disabled (`disable_token = [29900, 29896, ...]`), then the outer `while True` loop continues; on later calls `cur_generation_with_func` re-inserts the earlier recorded calls over their result spans. — [inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py)
- Inference adds a scalar bias to the toolken logits: `logits_func += self.logits_bias` (set via `set_bias`); the README's commands use `--logits_bias 3.0` for GSM8K-XL, `2.7` for FuncQA one-hop, `4.0` for FuncQA multi-hop, `10.0` for VirtualHome and `10` for KAMEL. — [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py); [README](https://github.com/Ber666/ToolkenGPT)

**Calc-X / Calcformers (Kadlčík et al., EMNLP 2023, arXiv 2305.15017; prompteus/calc-x)**
- Format (§3, Fig. 2): calls are `<gadget id="calculator">27/3</gadget>` followed by `<output>9</output>`, and the final answer is wrapped as `<result>18</result>`. Repo example: `Mike got 2/5*$2500 = $<gadget id="calculator">2/5*2500</gadget><output>1_000</output> 1000` ... `Final result is<result>800</result></s>`. — [Calc-X §3, ar5iv](https://ar5iv.labs.arxiv.org/html/2305.15017); [calc-x README](https://github.com/prompteus/calc-x)
- Stop/insert (Fig. 1 caption, verbatim): "By generating the closing </gadget> tag, model calls an external tool." "The following tokens are inserted into the model's context by the tool." §5: the model's text is extended with sympy output "whenever the model generates the enclosing gadget tags." and "We use greedy decoding in inference." The repo patches generation: `GadgetAssistedT5 = gadget_assisted_model(T5ForConditionalGeneration)`, `model.prepare_for_generate(tokenizer, enabled_gadgets=[Calculator()], default_max_tokens=512)`; "We patch the `generate()` method to be able to enable the given set of tools (functions) during the generation." — [Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017); [calc-x README](https://github.com/prompteus/calc-x)

**Chat-template function calling (Hugging Face transformers / TRL and model templates)**
- Standard flow (verbatim steps): "1. Parse the model's output to get the tool name(s) and arguments. 2. Add the model's tool call(s) to the conversation. 3. Call the corresponding function(s) with those arguments. 4. Add the result(s) to the conversation". Example model output: `<tool_call>\n{"arguments": {"location": "Paris, France", "unit": "celsius"}, "name": "get_current_temperature"}\n</tool_call><|im_end|>`; the result is appended as `{"role": "tool", "tool_call_id": tool_call_id, "name": "get_current_temperature", "content": "22.0"}`; the next generation is "The current temperature in Paris, France is 22.0 ° Celsius.<|im_end|>". — [HF chat_templating v4.44](https://huggingface.co/docs/transformers/v4.44.0/en/chat_templating)
- Template-writing guidance: tool calls live in the `tool_calls` key of an `assistant` message and a common rendering is `'<tool_call>' + tool_call['function']['name'] + '\n' + tool_call['function']['arguments']|tojson + '\n</tool_call>'`; tool responses are `tool`-role messages (`{"role": "tool", "name": "multiply", "content": "30"}`) rendered e.g. as `"<tool_result>" + message['content'] + "</tool_result>"`; "Formatting such as whitespace and special tokens are model-specific. Make sure everything exactly matches the format a model was trained with." — [HF chat_templating_writing](https://huggingface.co/docs/transformers/main/en/chat_templating_writing)
- Production example (SmolLM3-3B template): the assistant branch is `{% generation %}{{ "<|im_start|>assistant\n" + content.lstrip("\n") + "<|im_end|>\n" }}...{% endgeneration %}`; a `tool`-role message is rendered as `{{ "<|im_start|>" + "user\n" + content + "<|im_end|>\n" }}` (i.e. as a user turn, outside the generation block); tool calls use `<tool_call>\n{"name": <function-name>, "arguments": <args-json-object>}\n</tool_call>`. — [SmolLM3-3B chat_template.jinja](https://huggingface.co/HuggingFaceTB/SmolLM3-3B/raw/main/chat_template.jinja)
- Function-calling papers' surface formats (no execution loop in the training text): Granite-20B-FunctionCalling: "we use <function_call> tag to represent a function in JSON form" (name/arguments keys) and function outputs appear as `<function_response>` blocks; APIGen/xLAM: prompt blocks `[BEGIN OF TASK INSTRUCTION]`, `[BEGIN OF AVAILABLE TOOLS]`, `[BEGIN OF FORMAT INSTRUCTION]`, `[BEGIN OF QUERY]`, output `{"tool_calls": [{"name", "arguments"}...]}` with "If no function call is needed, please make tool_calls an empty list '[]'"; ToolACE evaluation prompts require "[func_name1(params_name1=params_value1, params_name2=params_value2...), func_name2(params)]"; Gorilla: "The output of Gorilla is an API to be invoked." with the retriever-aware suffix "Use this API documentation for reference: <retrieved_API_doc_JSON>". — [Granite-FC](https://arxiv.org/html/2407.00121); [APIGen](https://arxiv.org/html/2406.18518); [ToolACE](https://arxiv.org/html/2409.00920); [Gorilla](https://ar5iv.labs.arxiv.org/html/2305.15334)

### Inferences
- **[inference]** The three "inline" designs differ in what the stop signal costs: Toolformer needs a learned 2-character sequence (`->`) that the model must emit; GSM8K reuses an ordinary `=` already present in arithmetic text; ToolkenGPT adds one new output row per tool so the stop signal is a single sampled id. For a model whose vocabulary already maps every integer 0-255 to one token, the GSM8K pattern `<<a+b=` followed by a tool-written single result token and `>>` is the most token-frugal (about 5 tokens of overhead per call if `<<`, `>>`, `+` and `=` are single tokens), whereas Toolformer's `[Calculator(a + b) -> r]` costs roughly double.
- **[inference]** GSM8K's code "pre-empts" rather than "overwrites": because the check runs immediately after the `=` token is produced, no result tokens have been sampled yet, so the system simply appends `str(answer) + ">>"`. The paper's wording "overwriting the token(s) directly following "="" describes the same effect.
- **[inference]** GPT-2 ids 28 and 796 are most likely `=` and ` =`; id 47505 is another `=`-containing merge. Not verified (no GPT-2 tokenizer was available locally). For the tiny model with its own vocabulary, the equivalent is simply "the id of the `=` token"; if the tokenizer can merge `=` with neighbours, every such merge must be in the trigger set, or the calculator silently never fires.
- **[inference]** ToolkenGPT's LLaMA stop ids `29897` and `3892` are most likely `)` and `)=`, i.e. the argument generation ends at the closing parenthesis. Not verified.
- **[inference]** In ToolkenGPT the text the model later conditions on contains only the result (`... = 501`), not the call; the call is kept in a side list and re-inserted only when building the next tool-mode prompt. In Toolformer and GSM8K the call stays in the context. For a 64-token context, ToolkenGPT's "strip the call, keep the number" is the most context-efficient at inference, but it means the model never sees its own call text while continuing.

## Key question 2: In training, is the tool's result token in the LM loss or masked out, and what reasons are given?

### Takeaway
GSM8K trains on the full annotated text with no distinction ("they are all just tokens") and relies on test-time override; Toolformer fine-tunes on the augmented corpus with "a standard language modeling objective" and does not mention masking the response; ToolkenGPT explicitly masks the result positions (`[N/A]`, `-100`) and trains only the toolken embeddings; Calc-X reports cross-entropy "on all tokens"; the chat-template/TRL ecosystem masks everything the environment supplies (tool responses, user, system) and scores only the assistant's own tokens including the tool-call JSON, with the stated reason that the model should not be trained to generate tool outputs.

### Cited Findings
- GSM8K, Appendix C (verbatim): "During training, there is no special distinction between the annotated tokens and the rest of the solution: they are all just tokens. During testing, we override model sampling when a well-formatted annotation exists, specifically overwriting the token(s) directly following "=" and within <<…>>." — [GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)
- Toolformer, §2: "We use this new dataset to finetune M, using a standard language modeling objective." and "apart from inserted API calls the augmented dataset C* contains the same texts as C". The inserted calls are `e(c, r)`, i.e. they include the response `r`. No sentence about masking the response was found in §2, §4 or Appendix A/B. — [Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)
- ToolkenGPT, §3.2 (verbatim): "To indicate when to predict the toolkens, we need a parallel sequence mixed with word tokens and toolkens, i.e. s′ = ("the", "area", "is", "[square]", "[N/A]", "[N/A]", "square", "feet", …). The subsequence of ("2", "5", "6") in s is where the returned tool results should fill in, and we choose the corresponding first token in s′ as the toolken for the tool call with the following tokens are filled with [N/A], indicating neglect in loss calculation." Objective (2): L(W_τ) = Σ_{(s,s′)∈D} Σ_{i=1}^{N} −log P(t′_i | t_<i) · 1[t′_i ≠ [N/A]], "the indicator function signaling we ignore the [N/A] tokens during the training ... Here, [N/A] is introduced to skip the generation of the returned value of a tool call." Also: "This embedding matrix contains the only parameters to optimize ... it does not require the gradients flowing through the major body of LLM parameters". — [ToolkenGPT §3.2](https://ar5iv.labs.arxiv.org/html/2305.11554)
- ToolkenGPT code implements exactly this: `self.func_embed = nn.Linear(base_model.params.dim, len(func_dict), bias=False)`; `for param in self.model.parameters(): param.requires_grad = False`; in `get_loss`, for each annotated span `(s, t, eq)` it sets `labels[s] = self.func_dict[op] + 32000` and `labels[s+1: t] = -100`; with `only_functoken=True` it additionally does `labels[labels < 32000] = -100`; logits are `concat_logits = torch.cat([token_logits, func_logits], dim=-1)` and the loss is `F.cross_entropy(concat_logits.view(-1, concat_logits.shape[-1]), labels.view(-1), ignore_index=-100)`. — [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py); the trainer calls `funcmodel.get_loss([prompt], only_functoken=only_functoken)` with `only_functoken=False` by default and optimizes only `[p for p in funcmodel.parameters() if p.requires_grad]` — [train_llama.py](https://github.com/Ber666/ToolkenGPT/blob/main/train_llama.py)
- Calc-X: Appendix A.1 describes "standard sequence-to-sequence training with cross-entropy loss on all tokens"; §5: "using teacher forcing and cross-entropy loss". No statement about masking `<output>` tokens. — [Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017)
- Hugging Face `apply_chat_template` docstring (verbatim): "return_assistant_tokens_mask (`bool`, defaults to `False`) : Whether to return a mask of the assistant generated tokens. For tokens generated by the assistant, the mask will contain 1. For user and system tokens, the mask will contain 0. This functionality is only available for chat templates that support it via the `{% generation %}` keyword." — [HF tokenization_utils](https://huggingface.co/docs/transformers/main/en/internal/tokenization_utils)

- SmolLM3-3B's shipped template puts `{% generation %}...{% endgeneration %}` around the assistant branch only; `tool`-role messages are rendered as user turns outside it. — [SmolLM3-3B chat_template.jinja](https://huggingface.co/HuggingFaceTB/SmolLM3-3B/raw/main/chat_template.jinja)
- Practitioner guidance (verbatim): "If the model should generate tool calls, include the assistant tool-call tokens." - Stated reason (verbatim): "Then the loss is computed over the assistant's outputs only." "That includes the raw JSON inside the tool call." - A TRL issue requests loss "only on assistant text and tool-call parts, with tool content hidden", indicating this was not a one-flag feature at the time (Dec 2024). — [huggingface/trl issue #2429](https://github.com/huggingface/trl/issues/2429)

### Inferences
- **[inference]** "Masking the result" never removes the result from the model's input; it only removes the target at that position. In ToolkenGPT the result token is still read by all later positions (the loss at those positions is kept), so the model is trained to use the result without being trained to produce it. This is the behaviour the tiny model wants: it should learn to copy/consume `r` after `=` but not spend 4 layers of capacity on computing `r`.
- **[inference]** GSM8K's "all just tokens" choice means a fine-tuned model is also trained to do the arithmetic itself; the calculator then merely repairs its errors at test time. For a 128-dim model the arithmetic head-room is the scarce resource, so the ToolkenGPT/TRL convention (label = -100 at the result token) is the better default, with GSM8K's full-loss variant as a controlled ablation.
- **[inference]** Toolformer's self-supervised filter needs the response in the loss *during data selection* (L_i^+ conditions on `e(c, r)`), but nothing in the filter requires the response to be a training target during fine-tuning; a masked-response fine-tune is compatible with the Toolformer data pipeline.

### Gaps
- Whether Toolformer masks response tokens during fine-tuning is not stated either way; the "standard language modeling objective" sentence is the only evidence, and I read it as "no masking".
- Calc-X never states explicitly whether `<output>` tokens are masked; "cross-entropy loss on all tokens" suggests not.
- IBM's Granite 3.0 technical report reportedly says that control sequences and user and tool inputs are excluded from the post-training loss (search-result snippet), but the report is only available as a PDF that could not be text-extracted here, so this is unverified. — [Granite 3.0 report (PDF)](https://github.com/ibm-granite/granite-3.0-language-models)

## Key question 3: How does the model learn WHEN to call, and how are malformed or unnecessary calls handled at decode time?

### Takeaway
Toolformer learns "when" from its own loss-reduction filter (keep a sampled call only if conditioning on call+result lowers the weighted loss on the next tokens by at least τ_f versus no call or call-without-result), then biases decoding toward calling (start a call whenever `<API>` is among the top-k=10 tokens, at most one call per input); GSM8K relies entirely on fixed annotations in the training text and the calculator simply declines to fire on malformed expressions; ToolkenGPT trains the toolken logit at the exact position where a result begins, with every other position acting as a "don't call here" negative, and adds a tunable logit bias plus try/except backtracking at decode time.

### Cited Findings

**Toolformer**
- Candidate positions, §2: `p_i = p_M(<API> | P(x), x_{1:i−1})`; keep positions with `p_i > τ_s`, "if there are more than k such positions, we only keep the top k"; "we then obtain up to m API calls" per position by decoding from the prefix ending in `<API>` with `</API>` as end-of-sequence; footnote 2: "We discard all examples where M does not generate the </API> token." — [Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Filter, §2: `L_i(z) = −Σ_{j=i}^{n} w_{j−i} · log p_M(x_j | z, x_{1:j−1})`; `L_i^+ = L_i(e(c_i, r_i))`; `L_i^- = min(L_i(ε), L_i(e(c_i, ε)))`, "the minimum of the losses obtained from (i) doing no API call at all and (ii) doing an API call, but not providing the response"; keep iff `L_i^- − L_i^+ ≥ τ_f`, i.e. "adding the API call and its result reduces the loss by at least τ_f, compared to not doing any API call or obtaining no result from it." Footnote 3: the call is given "as a prefix instead of inserting it at position i because M is not yet finetuned on any examples containing API calls". — [Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Weights and hyperparameters, Appendix A: `w_t = w̃_t / Σ_s w̃_s` with `w̃_t = max(0, 1 − 0.2·t)` (so only the five tokens after the call count); defaults `τ_s = 0.05`, `τ_f = 1.0`, `k = 5`, `m = 5`; for the calculator (and machine translation) `τ_s = 0.0`, `k = 20`, `m = 10`, `τ_f = 0.5`; calculator source documents must contain "at least three numbers within a window of 100 tokens". Kept calculator examples: 3,680 (τ_f=0.5) / 994 (1.0) / 138 (2.0), versus 207,241 / 60,974 / 13,944 for Wikipedia search (Table 2). — [Toolformer Appendix A / Table 2](https://ar5iv.labs.arxiv.org/html/2302.04761v1)
- Decode-time disposition, §4.2 (verbatim): "We use standard greedy decoding, but with one modification for Toolformer: We let the model start an API call not just when <API> is the most likely token, but whenever it is one of the k most likely tokens. For k=1, this corresponds to regular greedy decoding; we instead use k=10 to increase the disposition of our model to make use of the APIs that it has access to. At the same time, we only at most one API call per input to make sure the model does not get stuck in a loop where it constantly calls APIs without producing any actual output." Disabling calls is "achieved by manually setting the probability of the <API> token to 0." (footnote 5). — [Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)
- On unfiltered noise, §5 (verbatim): "some amount of noise in the API calls that are not filtered can actually be useful as it forces the model finetuned on C* to not always blindly follow the results of each call it makes." Table 10 shows the filter rejecting a wrong-argument calculator call (`Calculator(85 / 23) → 3.70` before "65% had a cardiac aetiology", score −0.02, ✗) and accepting a useful one (`Calculator(735 / 499) → 1.47` before "1.47 (735 / 499) times hotter", score 1.59, ✓). — [Toolformer §5 / Table 10](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Limitations, §7 (verbatim fragments): "the inability of Toolformer to use tools in a chain"; "Our current approach also does not allow the LM to use a tool in an interactive way."; "models trained with Toolformer to often be sensitive to the exact wording of their input when deciding whether or not to call an API."; "Depending on the tool, our method is also very sample-inefficient."; "Toolformer currently does not take into account the tool-dependent, computational cost incurred from making an API call." — [Toolformer §7](https://ar5iv.labs.arxiv.org/html/2302.04761)

**GSM8K**
- When-to-call is fixed by the annotations: "The calculator annotations were not provided by human contractors: they were generated by a combination of hard-coded logic and a finetuned language model. The logic for auto-generating calculator annotations is imperfect. It is highly unlikely to generate any incorrect annotations, but it is not uncommon for it to ignore some lines that could be annotated." — [GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)
- Malformed calls: "Evaluations that time out or throw an error result in the annotations being skipped and the model being sampled from as usual." In code, `use_calculator` returns `None` (no override) when the expression contains any character outside `"0123456789*+-/.()"` or when `eval` fails/times out; the loop then just keeps sampling, so the model writes the result itself. A value of `0` is a valid answer and is appended. — [GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168); [calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py)

**ToolkenGPT**
- When-to-call is supervised at the token level: objective (2) above sums over every non-`[N/A]` position, with the toolken as the target at the position where the result begins. Training data come from "datasets [that] provide ground truth tool calls" or "synthetic data generated by LLMs"; GSM8K-XL training pairs were built by preprocessing "the original training set of GSM8K which has the calculation annotation" (5,054 train / 1,000 validation per §4.1; Appendix A.1.2 says 5,063 — the two figures conflict); FuncQA has 611 synthetic training samples and 39 validation samples. — [ToolkenGPT §3.2, §4.1](https://arxiv.org/html/2305.11554)
- Decode-time knobs: `logits_func += self.logits_bias` (values 2.7-10 per task in the README); `disable_func` / `disable_token` set chosen logits to `-1e5`. — [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py); [README](https://github.com/Ber666/ToolkenGPT)
- Malformed calls: the function call is wrapped in a bare `try`/`except`; on failure the code backtracks to the next-most-likely logged token (`current_token += 1`; `cur_generation = cur_generation.split(op)[0] + decode_token(record_tokens[1][current_token][0])`) and the failed call is not kept; an unparseable argument string raises `Exception("invalid args")`, which ends the generation with `"status": str(e)`. There is no cap on the number of calls in `func_embedding_inference` (the cap `max_func_call` exists only in the VirtualHome and KAMEL modes). — [inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py)
- Training hyperparameters: lr `1e-3` and 10 epochs for GSM8K-XL, `1e-4` for FuncQA (README); the paper's appendices give "Toolken embeddings are trained with a learning rate of 1e-4" with early stopping and a maximum of 5 (B.3) or 10 (C.3) epochs. — [README](https://github.com/Ber666/ToolkenGPT); [ToolkenGPT appendix](https://arxiv.org/html/2305.11554)

**Chat-template SFT**
- There is no learned "when" beyond imitation: the model is trained on assistant turns that contain either text or a `tool_calls` block; the trainer scores the tool-call JSON and masks the rest. — [TRL SFT Trainer](https://huggingface.co/docs/trl/main/en/sft_trainer); [TRL chat templates](https://huggingface.co/docs/trl/main/en/chat_templates)
- Data pipelines handle bad calls by filtering before training: APIGen's three-stage "Format Checker", execution checker and "Semantic Checker" (e.g. for DeepSeek-V2-Chat: 817 fail format, 3,359 fail execution, 2,165 fail semantic, 33,659 verified out of 40,000), and adding the filtered-out data back "harms the final performance"; ToolACE uses "a rule checker" plus "LLMs to filter out erroneous data that cannot be detected by the rule checker"; xLAM shuffles tool order "To avoid model overfitting to the specific order of the tools" and uses 15 output formats. — [APIGen](https://arxiv.org/html/2406.18518); [ToolACE](https://arxiv.org/html/2409.00920); [xLAM](https://arxiv.org/html/2409.03215)

### Inferences
- **[inference]** Because ToolkenGPT's LM is frozen and the loss includes word-token positions, the only way the gradient can lower the loss at a word position is by pushing the toolken logits down there; so Eq. (2) simultaneously teaches "call here" (positive) and "don't call here" (negative). The `only_functoken` flag removes the negatives. For the tiny model, which is trained end-to-end, the same effect comes for free from ordinary next-token loss on annotated text, provided the training text contains both annotated arithmetic and ordinary numbers that are not computed.
- **[inference]** Toolformer's filter cannot be run as published on a 4-layer model, because step one (prompting the model to propose calls) presumes instruction following. But the *scoring* half is model-agnostic: one can insert rule-generated candidate calls at every arithmetic equation and keep only those that lower the tiny model's own loss on the following tokens by τ_f. That would answer "is a call worth its tokens here?" with the model's own perplexity, as Toolformer intends.
- **[inference]** The two decode-time dials that transfer directly to a small GPT are Toolformer's "start a call if `<API>` is in the top-k" and ToolkenGPT's additive logit bias on the call token; both exist precisely because fine-tuned models under-call.

### Gaps
- No source quantifies how often Toolformer or ToolkenGPT produce syntactically malformed calculator calls at test time; only the handling code is documented.
- Toolformer's Table 9 (effect of k on decoding) was not extracted; only the k=10 choice and its rationale are recorded.

## Key question 4: What accuracy did a calculator give on math word problems (numbers, model sizes), and what is said about wrong-argument calls versus misusing a right result?

### Takeaway
Toolformer (GPT-J 6.7B) went from 14.8/6.3/15.0 (calls disabled) to 40.4/29.4/44.0 on ASDiv/SVAMP/MAWPS, calling the calculator on 97.9% of examples and beating GPT-3 175B; ToolkenGPT (LLaMA-33B) scored 0.33 on GSM8K-XL and 0.73/0.15 on FuncQA one-/multi-hop versus ReAct's 0.32/0.57/0.06; Calcformers (T5 700M-3B) doubled or tripled baseline accuracy (e.g. GSM8K 17.0 → 34.2 for T5-L); T5-XXL CoT-distilled went from 21.99% to 38.21% on GSM8K with a post-hoc calculator. GSM8K itself reports no with/without-calculator ablation. None of the papers separately counts wrong-argument calls versus misuse of a correct result; the closest statements are Toolformer's Table 10 scoring and ToolkenGPT's remark that ReAct is "making wrong tool calls, and predicting wrong arguments".

- **[inference]** Toolformer's "disabled" vs enabled rows isolate the tool's contribution on the same weights: roughly +25 to +29 absolute points on the three datasets for a 6.7B model. - **[inference]** The literature consistently treats "wrong argument" errors as data-quality problems to be filtered (Toolformer's τ_f, APIGen's execution checker) rather than as a behaviour to be measured per call at test time; nobody reports a confusion matrix of {right call, wrong args, right result misused}. For the tiny model this is a measurement worth building, since all three cases are observable (the ALU can log the operands it received).

### Gaps
- No paper in this set reports a per-call breakdown of wrong-argument calls versus misuse of a correct result.
- GSM8K's model sizes with/without calculator were not re-verified from the paper text in this pass (the calculator ablation does not exist in the paper); Toolformer's Figure 4 per-size numbers are only in a plot.

## Key question 5: Has a model under 100M parameters been trained to use a calculator or tool this way, and what happened?

### Takeaway
Yes, with a supervised recipe: Magister et al. (2022) fine-tuned T5-small (60M) on distilled chain-of-thought and report that "given an external calculator, even T5 small outperforms the baseline T5 XXL" (11B, 8.11% on GSM8K), though their calculator is a post-hoc equation re-computation rather than a learned call token and the exact T5-small number is only in a figure. Toolformer's self-supervised recipe did not help GPT-2 124M or 355M ("the ability to leverage the provided tools only emerges at around 775M parameters"). The GSM8K repo ships a GPT-2-scale train/sample pipeline with the calculator, but states it was not used for the paper's experiments.

### Cited Findings
- Magister et al., §5.2 (verbatim): "Figure 3 shows the performance gain achieved when finetuning T5 of different sizes on the GSM8K dataset. Our results show that T5 base, with 44 times fewer parameters than T5 XXL, matches the performance of the baseline T5 XXL when trained on CoT data. Moreover, given an external calculator, even T5 small outperforms the baseline T5 XXL." Sizes named in the paper: "T5 XXL, XL and base, which have 11 billion, 3 billion and 220 million parameters, respectively."; baseline T5 XXL on GSM8K = 8.11%. — [Magister et al. §5.2, Table 1](https://ar5iv.labs.arxiv.org/html/2212.08410)
- T5-Small size: "T5-Small is the checkpoint with 60 million parameters." — [google-t5/t5-small model card](https://huggingface.co/google-t5/t5-small)
- Magister's calculator mechanism (verbatim): "The external calculator moves through the generated output, recalculating the left hand-side of equations. It then replaces the right-hand side with the calculated output, to avoid arithmetic mistakes being carried forward. For example, if a model outputted '5 + 5 = 11. 11 * 2 = 22', then the external calculator would first calculate '5+5' and replace the '11' with a '10'. In the subsequent equation, it would also replace the '11' with a '10' and arrive at the final result of '20'." The training targets are the teacher's CoT text (Figure 2 shows the T5 input/output format); no call tokens are learned. — [Magister et al. §4](https://ar5iv.labs.arxiv.org/html/2212.08410)
- Toolformer with GPT-2 124M/355M/775M/1.6B: tools help only from ~775M; "smaller models achieve similar performance both with and without tools." — [Toolformer §4.4](https://ar5iv.labs.arxiv.org/html/2302.04761)
- Calc-X trained no model below 700M ("T5-L (700M)", "T5-XL (3B)", "Flan-XL (3B)") and "does not make any claim about small models benefiting". — [Calc-X §5](https://ar5iv.labs.arxiv.org/html/2305.15017)
- GSM8K repo: the README's GPT-2-based `train.py`/`sample.py` pipeline is described as for illustrative purposes only and not used for any experiments in the paper (paraphrased from the README via search summary; the README quotes above about `calculator.py:sample` and "Note that this code is inefficient as implemented." are verbatim). — [grade-school-math README](https://github.com/openai/grade-school-math)
- Smallest function-calling models in the surveyed papers: xLAM-1B (FC) (1.35B) at 74.41 BFCL; Hammer targets on-device models via "function masking" (a prompt-side masking of function names, not loss masking). — [APIGen](https://arxiv.org/html/2406.18518); [xLAM Table 1](https://arxiv.org/html/2409.03215); [Hammer](https://arxiv.org/html/2410.04587v2)

### Inferences
- **[inference]** The only positive sub-100M result (T5-small + calculator) comes from the simplest possible mechanism: the model writes ordinary `a op b = c` equations and the environment rewrites `c`. That is functionally identical to GSM8K's `<<a op b=` trigger with the result token overridden, which is the recipe to copy for the 4-layer GPT: fixed annotations, ordinary next-token loss, and an override on the single result token.
- **[inference]** Toolformer's negative result at 124M is about *self-supervised discovery* of when to call on open-domain CCNet text with a 1,024-token context, not about whether a small model can execute a fixed, supervised call format; so it does not predict failure for the TinyStories+arithmetic setting.
- **[inference]** With single-token integers 0-255 and an 8-bit ALU, the override is exactly one token, so the "misuse of a right result" failure mode reduces to whether the model copies the token after `>>`/`=` into its final answer line; Magister's carry-forward replacement (fixing later uses of a wrong intermediate) is unnecessary when the result is overridden at generation time.

### Gaps
- The exact GSM8K accuracy of T5-small with the calculator is shown only in Magister et al.'s Figure 3 (an image) and was not recoverable as text.
- No published work was found that trains a model under 100M parameters with a *learned call token* (Toolformer/ToolkenGPT style) for a calculator; the closest are T5-small with post-hoc recomputation and the unused GPT-2 illustration pipeline in the GSM8K repo.
- No results were found for tool use with a 64-token context or with a single-token-per-integer vocabulary.

## Key question 6 (synthesis for the target model): Which of these mechanics transfer to a 4-layer, d_model-128, 64-token GPT with an 8-bit +/-/x CPU?

### Takeaway
The supervised, fixed-annotation route (GSM8K format, ToolkenGPT-style loss mask on the result token, Toolformer/ToolkenGPT-style decode-time bias) is the only one whose preconditions the tiny model meets; the self-supervised Toolformer data pipeline and the chat-turn function-calling format both assume capabilities (prompt following, long contexts, JSON) it lacks.

### Cited Findings
- Format cost drivers come from the sources above: Toolformer's call includes a tool name, parentheses, the expression, `->`, the result and `]` (§2, fn.1); GSM8K's is `<<expr=result>>` (README); ToolkenGPT's is one extra vocabulary row per tool plus the result (§3.1-3.2). — [Toolformer](https://ar5iv.labs.arxiv.org/html/2302.04761); [grade-school-math](https://github.com/openai/grade-school-math); [ToolkenGPT](https://ar5iv.labs.arxiv.org/html/2305.11554)
- Loss-mask mechanics: `labels[s] = func_id + 32000; labels[s+1:t] = -100` and `F.cross_entropy(..., ignore_index=-100)` (ToolkenGPT code); HF/TRL use the same `-100` ignore index and a `{% generation %}` block to mark scored spans. — [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py); [TRL SFT Trainer](https://huggingface.co/docs/trl/main/en/sft_trainer)
- Error handling precedents: skip-on-failure and continue sampling (GSM8K `use_calculator` returns `None`); backtrack to next-best token on exception (ToolkenGPT); one call per input to avoid loops (Toolformer §4.2). — [calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py); [inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py); [Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)

### Inferences
- **[inference]** Call syntax: use GSM8K's shape but with the model's own single tokens, e.g. `<<` `12` `+` `5` `=` then the ALU writes `17` and `>>`. Decoding stops on the `=` id (GSM8K) or, more robustly, on a dedicated `<calc>`-style special id (ToolkenGPT), which avoids any ambiguity with `=` used in prose. Because every integer is one token, the ALU's output is exactly one token and `>>` one more.
- **[inference]** Training labels: ordinary next-token loss on the whole annotated story, except set the label at the result position to -100 (ToolkenGPT `[N/A]`); keep the loss on `<<`, the operands, the operator, `=`, and on `>>` and everything after, so the model learns to open calls, write arguments, close them, and read the result. Run GSM8K's "all just tokens" variant as the ablation to see whether a 128-dim model wastes capacity trying to learn 8-bit addition.
- **[inference]** When to call: inherit it from the data (annotate every arithmetic step the way GSM8K does, and keep un-annotated numbers elsewhere so the model does not learn to call at every digit). If under-calling appears at test time, add a logit bias to `<<`/`<calc>` (ToolkenGPT) or trigger when it is in the top-k (Toolformer, k=10), and cap calls per 64-token window to avoid Toolformer's loop failure.
- **[inference]** Malformed calls: validate the expression exactly as `use_calculator` does (whitelist of characters, operands in 0-255, operator in {+,-,x}); on overflow or invalid input either skip the override and let the model continue (GSM8K) or emit a fixed error token the model has seen in training; log operands so wrong-argument calls can be counted separately from misuse of a correct result (the gap no paper fills).
- **[inference]** Context budget: at 64 tokens a Toolformer-style call (~10+ tokens) would consume a sixth of the window; the GSM8K shape (~6 tokens) or ToolkenGPT's "strip the call, keep the result" (1 token left behind) are the only affordable options.

### Gaps
- Nothing in the literature tests whether a model this small can learn to *emit* the opening of a call at the right moment; the Toolformer scaling result is the only negative signal and it is confounded by self-supervision and task domain.
