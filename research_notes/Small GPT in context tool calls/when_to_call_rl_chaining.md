# Learning WHEN to call a tool, and how to chain calls: methods, rewards, findings (ReAct/PAL/PoT, ToRA, ReTool, ToolRL, ARTIST, Toolformer, over-calling penalties)

Scope note for the report writer: everything below was checked against the primary papers (arXiv full texts were extracted locally for ToRA, ReTool, ToolRL, ARTIST, OTC, Toolformer, Calc-X, ToolkenGPT, GSM8K, ReAct, PAL, PoT and "Spurious Tool Use"; the remaining sources were read through fetched HTML/abstract pages, so numbers from those are second-hand extractions and are marked "(via fetched page)"). Reader context used in the Inferences: a 4-layer, d_model=128 GPT with 64-token context, trained from scratch on TinyStories + inserted word problems, numbers 0-255 as single tokens, tool = 8-bit CPU doing +, -, x, and an existing REINFORCE loop with a result-check reward.

## Key question 1: What reward signals are used for the call decision (final-answer correctness, per-call cost, format rewards, loss reduction on following tokens), and what did ablations show about each?

### Takeaway
Every RL system surveyed makes final-answer correctness the backbone reward and masks tool-output tokens from the loss; the main design disagreements are (i) whether to add a format reward (Nemotron: yes, binary, +2.9 points; Search-R1: skipped it; ToolRL: keep it smaller than correctness), (ii) whether to add a per-call cost (OTC, EAPO, AdaTIR, "Spurious Tool Use" all find outcome-only rewards produce unnecessary calls and fix it with a multiplicative or additive efficiency/necessity term that only applies to correct answers or unnecessary calls), and (iii) Toolformer's pre-RL alternative: keep a call in the training data only if it lowers the LM loss on the following tokens by at least a threshold.

### Cited Findings

Outcome-only rewards (and what they produce)
- ReTool uses a pure rule-based accuracy reward, R(a, â) = 1 if is_equivalent(a, â) else −1, with the final answer required in \boxed{}; the authors "simplify the reward design [to] alleviate reward hacking and promote more diverse problem-solving behaviors based on mere outcome feedback without considering code executability reward" — [ReTool (Feng et al. 2025), §2.3.1](https://arxiv.org/abs/2504.11536)
- With that reward alone, ReTool (Qwen2.5-32B-Instruct) reaches 67.0% AIME2024 / 49.3% AIME2025 after 400 RL steps vs 40.0% / 36.7% for text-only RL after >1000 steps (1080); cold-start SFT alone gives 40.9% / 34.5%; the untrained base 26.7% — [ReTool, Table 1](https://arxiv.org/abs/2504.11536)
- Under this outcome-only reward the code ratio (fraction of responses containing code) rises to "nearly 98% percent of all questions", average code lines become "nearly fivefold higher than that before RL", total correct code counts on the test set rise "from 1k to 5k", average response length falls 40% ("from 10k to 6k" tokens), and the "code invocation timing" (start position of code / response length) "advances during the RL training process, indicating that the model learns to determine the timing for tool usage" — [ReTool, §3.3 and Fig. 3](https://arxiv.org/abs/2504.11536)
- ToRL uses correctness reward +1 / −1 and tested an extra "executability penalty" (executable 0, unexecutable −0.5); "adding the penalty does not improve performance" and the authors hypothesize it pushes the model toward overly simple code; the penalty is omitted by default (via fetched page) — [ToRL (Li et al. 2025)](https://arxiv.org/abs/2503.23383)
- Search-R1 uses only an exact-match outcome reward and explicitly skips a format reward because the model "already demonstrates strong structural adherence"; the paper does not discuss over-calling, and the only related example is an extra search used for self-verification after the answer was already supported (via fetched page) — [Search-R1 (Jin et al. 2025)](https://arxiv.org/abs/2503.09516)
- ARTIST trains "using only outcome-based rewards" in the sense of no step supervision, but its composite reward for math is: Answer reward 2 if exact match else 0; relaxed format reward 0.125 per present tag pair (<think>, <python>, <output>, <answer>) up to 0.5; strict format reward +0.5 if all tags present, properly nested, and in the order <think> → <python> → <output> → <answer>; Tool Execution Reward = Tool_success / Tool_total ∈ [0, 1] — [ARTIST (Singh et al. 2025), §2.4 and §3](https://arxiv.org/abs/2505.01441)
- Under that reward ARTIST's call rate adapts to difficulty: "On AIME, the base model averages only 0.3 tool calls per query, whereas ARTIST averages over 3 tool calls per query ... on MATH 500, ARTIST reduces tool usage compared to the baseline, suggesting that it selectively avoids unnecessary tool calls when internal reasoning suffices" — [ARTIST, §5.1.2](https://arxiv.org/abs/2505.01441)

Format rewards: binary vs partial credit
- Nemotron-Research-Tool-N1 uses a binary reward r = 1 only if the output contains both <think> and <tool_call> tags AND the parsed call matches the ground truth (function name and all required arguments, order-insensitive), else 0. Ablation on BFCL (Tool-N1-7B, Non-Live / Live / Avg): binary with reasoning-format constraint 89.25 / 80.38 / 84.82; fine-grained partial credit (0.2 for format) 87.83 / 79.64 / 83.74; fine-grained with 0.2 format + 0.2 for function-name match 88.54 / 76.61 / 82.58; binary WITHOUT the format constraint 87.63 / 76.24 / 81.94. The authors attribute the binary advantage to reduced reward hacking and say removing the reasoning-format constraint "significantly hurts performance" (via fetched page; note the paper's text compares 80.38 vs 76.61, which is the fine-grained+function-name column, not the plain fine-grained column) — [Nemotron Tool-N1 (Zhang et al. 2025), Table 4](https://arxiv.org/abs/2505.00024)
- Same paper, SFT vs RL on 5,518 R1-distilled trajectories (BFCL Avg): Reason-SFT 100% = 82.71; RL 100% = 83.24; Reason-SFT 50% + RL 50% = 83.17; the SFT-then-RL pipeline "does not necessarily outperform pure RL" (via fetched page) — [Nemotron Tool-N1, Table 3](https://arxiv.org/abs/2505.00024)
- ToolRL decomposes the reward as R_final = R_format + R_correct ∈ [−3, 4], with R_format ∈ {0, 1} ("all required fields appear and are in the correct order") and R_correct = 6·R_max/S_max − 3 ∈ [−3, 3], where the match score sums r_name = |N_G ∩ N_P| / |N_G ∪ N_P|, r_param (Jaccard over parameter names per ground-truth call) and r_value (fraction of parameter values equal), S_max = 1 + |G| + Σ|keys(G_j)| — [ToolRL (Qian et al. 2025), §3.3](https://arxiv.org/abs/2504.13958)
- ToolRL reward-scale ablation ("Equal Max": correctness rescaled to [−1, 1] to match format): overall BFCL accuracy drops for Qwen2.5-1.5B from 46.20% to 39.47% (irrelevance detection 56.44% → 16.44%), Llama-3.2-3B 44.10% → 42.47%; Qwen2.5-3B roughly unchanged (52.98% → 51.76%); conclusion: "assigning greater weight to correctness reward" matters — [ToolRL, Table 6 and §5.2](https://arxiv.org/abs/2504.13958)
- ToolRL dynamic scaling: an abrupt "Two stage" switch (correctness at 1/3 scale for the first s = 30 steps, then format halved) HURT (1.5B: 38.85%; 3B: 50.66%; Llama-3B: 41.33%), while a smooth linear interpolation Scale_format = [−2+p, 2−p], Scale_correct = [−2−p, 2+p] (p = normalized training progress) helped (3B: 53.81% vs 52.98% original; Llama-3B: 46.85% vs 44.10%; 1.5B: 45.71% vs 46.20%). "Takeaway 2: Gradually adjusting reward scales during training, rather than abrupt changes, better supports model learning and generalization" — [ToolRL, Table 6 and §5.2](https://arxiv.org/abs/2504.13958)
- ToolRL length reward R_length = min(L_think / L_target, 1) with L_target = 512 increased response length but hurt: Qwen2.5-1.5B overall 46.20% → 33.23% and irrelevance detection 56.44% → 4.52%; Qwen2.5-3B 52.98% → 48.89%; Llama-3.2-3B roughly flat (44.10% → 44.98%). "Takeaway 1: While length rewards encourage longer reasoning traces, they do not consistently improve task performance and may even harm it in smaller models" — [ToolRL, Table 5 and §5.1](https://arxiv.org/abs/2504.13958)
- ToolRL vs SFT: GRPO "trained from scratch on the Qwen2.5-Instruct series, generally outperforms other baselines, achieving ~10% absolute gains over SFT trained on the same data volume" (4K examples, or a selected 400); SFT-initialized models "achieve higher training rewards due to distributional alignment between SFT and RL data, but empirically generalize worse" — [ToolRL, §4.3](https://arxiv.org/abs/2504.13958)

Per-call cost / efficiency rewards (penalising over-calling)
- OTC-PO ("Acting Less is Reasoning More") introduces tool productivity TP = (number of correct answers) / (total tool calls) and a multiplicative reward r^tool_φ(q, y) = α · r_tool · r_φ(q, y), so "when the final answer is incorrect, r_φ is 0, effectively disabling the influence of r_tool", which "helps mitigate reward hacking by preventing the policy model from being incentivized to use tools without ultimately producing a correct answer" — [OTC (Wang et al. 2025), §3](https://arxiv.org/abs/2504.14870)
- OTC-PPO: r_tool = cos(m·π / (2m + c)), m = number of calls in the trajectory, c = "smooth constant that controls the reward decay rate" (set to the max tool limit). OTC-GRPO: r_tool = 1 if n = 0 and m = 0; cos(m·π/(2m + c)) if n = 0; sin(f(m, n)·π / (2n)) otherwise, with f(m, n) = 2nm / (m + n), where n is the minimum number of calls among the correct trajectories in the group (updated across epochs as a global approximation of the optimal count). The paper notes the framework "can be naturally extended to scenarios where the optimal tool call number is known a priori (e.g., n = 0 for language-only reasoning)" — [OTC, Eqs. 5-7](https://arxiv.org/abs/2504.14870)
- OTC evidence of over-calling in outcome-only RL: Search-R1-PPO (Qwen2.5-7B) averages 3.282 and 3.741 tool calls per question on the two QA groups of Table 1 (EM 0.449 / 0.380); OTC-PPO cuts this to 1.040 (−68.3%) with EM 0.446 and TP 0.136 → 0.429 (+215.4%). For the 3B model: 1.738 → 1.010 calls (−41.9%), EM 0.403 → 0.355. The paper observes "3B model tends to use less tool calls compared with 7B model ... as language models scale up, they may tend to over-rely on external tool calls unless explicitly penalized" — [OTC, Table 1 and §4.2](https://arxiv.org/abs/2504.14870)
- OTC with code as tool (ToRL baseline, max calls C = 3): Qwen2.5-Math-7B AIME24 EM 36.7 → 36.7 with calls 2.1 → 0.7 (−66.7%), TP 17.5 → 52.4; Qwen2.5-Math-1.5B EM 23.3 → 20.0 with calls 2.2 → 1.1 — [OTC, Table 2](https://arxiv.org/abs/2504.14870)
- "Learning When Not to Act" (EAPO) defines tool abuse as "redundant or excessive tool invocations, despite the existence of alternative solutions" (example: answering 1+1 with a calculator call) and shapes the reward as R̃_i = [d(q) + (1 − d(q))·ε(T_i)]·R_i with ε = exp(−β(c_i − c_min)), c_i = call count, c_min = minimum calls among correct rollouts (0 if none), d(q) = fraction of incorrect rollouts in the group (so hard queries keep the raw reward), base R_i = accuracy if format ok else −1, β = 1; at least n = 2 of M = 16 rollouts are generated with tools disabled. Ablation on HotpotQA: removing reward shaping raises tool calls per question from 1.99 to 3.49 (F1 54.1 → 51.2); on MATH 1.03 → 1.06 (90.0 → 87.6). The paper argues (qualitatively, no numbers) that uniform per-call penalties or hard call limits "may suppress useful exploration on genuinely challenging queries" and does not ablate a per-call cost or length penalty (via fetched page) — [EAPO (2026)](https://arxiv.org/abs/2606.02132)
- AdaTIR: difficulty φ_q = 1 − (1/G)Σ 1[passed], penalty f(τ) = sin((π/2)·N(τ)/N_max) with N_max = 4 ("steeper at the beginning", so the first calls are penalised most), r_eff = −λ·f(τ) only if the rollout is correct and φ_q < 0.8, total r = r_acc + r_eff. The paper reports a "sign reversal problem": when all rollouts are correct the advantage is "driven exclusively by efficiency", so correct rollouts with above-average tool use get negative advantages; fixed with clipped advantage shaping (β = 0.9, δ = 0.99); unclipped shaping hit "gradient explosion near step 1,100". Results (Qwen2.5-7B, GRPO baseline → AdaTIR, Avg@16 accuracy / avg tool calls): GSM8K 91.0 / 0.83 → 92.8 / 0.02 (−97.6% calls); AIME 2024 33.8 / 2.02 → 37.1 / 1.45 (−28.2%); AMC23 74.7 / 1.44 → 72.3 / 1.02. Baseline failure analysis: tool-induced noise accounts for 9.2% of GSM8K failures and 57.7% of AIME failures (via fetched page) — [AdaTIR (2026)](https://arxiv.org/abs/2601.14696)
- "Spurious Tool Use": standard RL "provides reward only on the final answer, leaving tool-selection decisions unsupervised. Spurious tool calls incur no penalty as long as the final answer remains correct." The fix is a dense necessity reward r_total = r_task + Σ_t r^nec_t with r^nec_t = −α if an LLM judge (GPT-5 Nano, given question, tool type and tool input) labels call t unnecessary, 0 otherwise, α = 0.5, penalising "only unnecessary calls to avoid incentivizing gratuitous tool use". Definition: "A tool call is necessary if a competent model cannot answer the question correctly without using that tool. Tool calls used purely for convenience (e.g., trivial arithmetic, formatting) are unnecessary." With the reward, cue-driven spurious search calls drop to 0.0-0.3% while accuracy is maintained or improved (e.g., cue <answer>: 48.8 / 57.4 → 55.2 / 57.2 with the reward) — [Spurious Tool Use (Yang et al. 2026), §4.1 and Table 1](https://arxiv.org/abs/2609.16268)

Loss reduction on following tokens as the call criterion (Toolformer)
- Toolformer samples candidate call positions with p_i = p_M(<API> | P(x), x_{1:i−1}), keeps positions with p_i > τ_s (top k), samples up to m calls per position, executes them, and keeps a call only if L⁻_i − L⁺_i ≥ τ_f, where L⁺_i = L_i(e(c_i, r_i)) is the weighted cross-entropy over tokens x_i..x_n given the call AND its result as prefix, and L⁻_i = min(L_i(ε), L_i(e(c_i, ε))) is the better of no call and call-without-result; weights w̃_t = max(0, 1 − 0.2·t) "to make sure that API calls happen close to where the information provided by the API is actually helpful" — [Toolformer (Schick et al. 2023), §2](https://arxiv.org/abs/2302.04761)
- Defaults τ_s = 0.05, τ_f = 1.0, k = 5, m = 5; for the calculator and MT tools τ_s = 0.0, k = 20, m = 10 and τ_f = 0.5 because the heuristically pre-filtered subsets are small (calculator candidates are only generated for texts with at least three numbers within a window). Resulting calculator examples: 3,680 (τ_f = 0.5), 994 (τ_f = 1.0), 138 (τ_f = 2.0), versus 207,241 / 60,974 / 13,944 for Wikipedia search — [Toolformer, Table 2 and Appendix A](https://arxiv.org/abs/2302.04761)
- Toolformer's authors note the filter is imperfect but usefully noisy: "some amount of noise in the API calls that are not filtered can actually be useful as it forces the model finetuned on C* to not always blindly follow the results of each call it makes" — [Toolformer, §5](https://arxiv.org/abs/2302.04761)

Loss masking of tool outputs (a design choice common to all RL systems)
- ReTool: "We mask out the <interpreter></interpreter> feedback output from the loss computation ... ensuring training stability" — [ReTool, §2.3.2](https://arxiv.org/abs/2504.11536)
- ARTIST: "Applying token-level loss uniformly can cause the model to imitate deterministic tool outputs, rather than learning effective tool invocation strategies. To prevent this, we employ a loss masking strategy: tokens from tool outputs are masked during loss computation" — [ARTIST, §2.2](https://arxiv.org/abs/2505.01441)
- Search-R1 ablation (PPO, average EM over 7 datasets): Qwen2.5-7B-base 0.431 with retrieved-token masking vs 0.343 without; 3B 0.303 vs 0.262 (via fetched page) — [Search-R1, Table 6](https://arxiv.org/abs/2503.09516)
- ToRL: "During loss computation, we mask out the OBSERVATION outputs from the sandbox environment" (via fetched page) — [ToRL](https://arxiv.org/abs/2503.23383)
- ToolkenGPT (supervised): result tokens are replaced by [N/A] in the parallel target sequence and ignored in the loss, "to skip the generation of the returned value of a tool call" — [ToolkenGPT (Hao et al. 2023), §3.2](https://arxiv.org/abs/2305.11554)
- Self-RAG (supervised) trains the generator with next-token prediction over text plus reflection tokens while it will "mask out the retrieved text chunks" (via fetched page) — [Self-RAG (Asai et al. 2023)](https://arxiv.org/abs/2310.11511)
- GSM8K's calculator baseline is the exception: "During training, there is no special distinction between the annotated tokens and the rest of the solution: they are all just tokens. During testing, we override model sampling when a well-formatted annotation exists, specifically overwriting the token(s) directly following "=" and within <<. . . >>" — [GSM8K (Cobbe et al. 2021), Appendix C](https://arxiv.org/abs/2110.14168)

### Inferences
- (Inference) For the reader's REINFORCE setup, the literature's consensus translates to: reward = 1[final number correct] as the base; multiply by an efficiency coefficient (OTC form) or subtract α per unnecessary call (Spurious form) rather than a flat per-call cost; never reward length. Because the synthetic generator knows the true number of arithmetic steps per problem, the optimal call count n is known a priori (0 for narrative sentences, 1 for one-step, 2 for two-step), which is exactly the case OTC says its sin-reward extends to without needing the group-minimum estimate.
- (Inference) The "sign reversal" and "exploration suppression" warnings (AdaTIR, EAPO) matter at small scale: with few rollouts per problem, a per-call penalty applied to correct answers can make a correct 1-call trajectory lose to a wrong 0-call one. Both papers' remedies (apply the efficiency term only when correct; scale it down on problems the model mostly fails) are cheap to implement.
- (Inference) Nemotron's and ToolRL's format results suggest keeping a small, binary format check (e.g., a call block must be well-formed, operand tokens must be numbers) while keeping its weight below the correctness reward, and avoiding abrupt reward re-weighting mid-training.
- (Inference) Toolformer's filter is a supervised-data analogue of the reader's question "would the call have helped?": in the reader's setting it can be computed exactly by comparing the model's loss on the answer token with and without the CPU result inserted, which could select which training positions get a call and which get no call.

### Gaps
- ToolRL's reward-granularity ablation (Section 5.3: finegrained vs intermediate vs coarse correctness) was not captured numerically in the extracted text; the paper's abstract-level claim is that finer granularity helps, but the table values are not in these notes.
- ReTool does not report any over-calling or unnecessary-call measure (its code ratio reaches ~98% on AIME, which are hard problems), and its cold-start dataset size is not stated in the extracted text.
- No source reports an ablation where a flat per-call cost is compared head-to-head with a length penalty; EAPO explicitly notes it did not run this comparison.

## Key question 2: How do these systems represent multi-step tool use in text (several call blocks in one answer; results copied into the next call), and how well do models chain 2+ calls? Any measurements of "copy the previous result correctly" errors?

### Takeaway
Two families exist: (a) one program per answer, where chaining is done by variables inside the program and the model never copies a number (PAL, PoT), and (b) inline interleaving, where each call block is followed by the tool's output and the model must re-read that output and write the next call (GSM8K <<>>, Calc-X <gadget>, Toolformer [..->..], ToRA/ToRL ```python/```output, ReTool <code>/<interpreter>, ReAct, ARTIST, Search-R1, ToolRL, ToolkenGPT). Chained calls are routinely produced (ToRA averages 1.02 rounds but up to n = 3; ReAct up to 5-7 steps; Calc-X 1.6 calls per chain; ARTIST >3 calls per AIME query), but no paper measures "copied the previous result wrongly" directly; the closest proxies are PoT's 47% "value grounding" errors and ToRA's 5% "hallucination: fabrication of numbers".

### Cited Findings

Exact trace formats (verbatim where the text allows)
- ReAct: trajectories are "multiple thought-action-observation steps (i.e. dense thought)"; the HotpotQA action space is search[entity] (first 5 sentences of the wiki page, else top-5 similar entities), lookup[string] (next sentence containing the string, "simulating Ctrl+F"), finish[answer]. Appendix example (Act-only shown; ReAct inserts "Thought i" lines before each action): "Action 1 Search[Colorado orogeny] / Observation 1 The Colorado orogeny was an episode of mountain building ... / Action 2 Lookup[eastern sector] / Observation 2 (Result 1 / 1) The eastern sector extends into the High Plains ... / Action 3 Search[High Plains] / ... / Action 5 Finish[1,800 to 7,000 ft]". Prompts use 6 (HotpotQA) and 3 (FEVER) exemplars; "We find more examples do not improve performance" — [ReAct (Yao et al. 2022), §3.1-3.2 and Appendix C](https://arxiv.org/abs/2210.03629)
- ReAct steps are capped: "more steps will not improve ReAct performance"; among correct trajectories, those with 7 steps on HotpotQA and 5 steps on FEVER make up only 0.84% and 1.33% — [ReAct, footnote 3](https://arxiv.org/abs/2210.03629)
- PAL: natural-language steps are written as Python comments ("# ..."), the program ends with an answer variable, and the interpreter runs the whole program once. Verbatim prompt example: "Q: Olivia has $23. She bought five bagels for $3 each. How much money does she have left? / money_initial = 23 / bagels = 5 / bagel_cost = 3 / money_spent = bagels * bagel_cost / money_left = money_initial - money_spent / answer = money_left". The paper notes "it is also possible to incrementally run the PL segments and feed the execution results back to the LLM to generate the following blocks" but did not do so — [PAL (Gao et al. 2022), §3 and Fig. 3](https://arxiv.org/abs/2211.10435)
- PoT: program ends in an ans variable under a "# Python code, return ans" header, e.g. "bolts_of_blue_fiber = 2 / bolts_of_white_fiber = num_of_blue_fiber / 2 / ans = bolts_of_blue_fiber + bolts_of_white_fiber". For multi-stage problems, demonstrations teach the model to emit 'keep prompting' at the end, after which "the execution results from PoT [are used] as input to further prompt LLMs to derive the answer through CoT" — [PoT (Chen et al. 2022), §2 and Appendix](https://arxiv.org/abs/2211.12588)
- Toolformer: a call with result is linearized as e(c, r) = <API> a_c(i_c) → r </API>; "In practice, we use the token sequences " [", "]" and "->" to represent "<API>", "</API>" and "→"" so no vocabulary change is needed; calculator I/O example from Table 1: input "27 + 4 * 2", output "35" — [Toolformer, §2 and Table 1](https://arxiv.org/abs/2302.04761)
- GSM8K calculator annotations: expressions are written as <<expression=result>> inside the solution text, generated "by a combination of hard-coded logic and a finetuned language model"; at test time the calculator (python eval) overwrites the tokens after "=" inside <<...>>, and "Evaluations that time out or throw an error result in the annotations being skipped and the model being sampled from as usual" — [GSM8K, Appendix C](https://arxiv.org/abs/2110.14168)
- Calc-X / Calcformers use three HTML-style tags (gadget, output, result). Verbatim target text: "After buying the bread and candy bar, you have 32-3-2= <gadget id="calculator">32-3-2</gadget> <output>27</output> $27. You spend 27/3= <gadget id="calculator">27/3</gadget> <output>9</output> 9 dollars on the turkey. You have 27-9= <gadget id="calculator">27-9</gadget> <output>18</output> $18 left. The final result is 18. <result>18</result>". At inference "By generating the closing </gadget> tag, model calls an external tool. The following tokens are inserted into the model's context by the tool. Finally, the model continues generation using all of the previous tokens." Calls are injected automatically wherever a regex finds "expression = number" and sympy agrees with the number, giving "1.6 calculator calls on average per single reasoning chain" — [Calc-X (Kadlčík et al. 2023), Figs. 1-2, §4](https://arxiv.org/abs/2305.15017)
- ToRA: trajectory τ = r1 a1 o1 ... r_{n−1} a_{n−1} o_{n−1} r_n (rationale, program, output), repeated "until the model places its answer within "\boxed{}""; execution is triggered when "the model triggers the code execution stop words like "```output"", the tool result o_i is appended, and generation continues; GPT-4 annotation used n = 3 maximum rounds — [ToRA (Gou et al. 2023), §2.1-2.2, Algorithm 1](https://arxiv.org/abs/2309.17452)
- ToRL: code in ```python blocks, execution output inserted as an ```output block containing the OBSERVATION; only the last line of a traceback is returned (e.g., "NameError: name 'a' is not defined"); default call limit C = 1 per response (C = 2 adds ~2% accuracy but raises step time from 237 s to 288 s; C = 0 is 118 s) (via fetched page) — [ToRL](https://arxiv.org/abs/2503.23383)
- ReTool: code between <code></code>; when </code> is detected "the generation pause and the generated code c1 is parsed and send to code sandbox"; "the sandbox's output f1 (successful results or error messages) is filled within <interpreter></interpreter> tags and fed back to the model, which continues generating the rollout until either providing a final answer o or producing a new code snippet, ultimately producing a hybrid reasoning trajectory [t1 ⊕ c1 ⊕ f1 ⊕ ... ⊕ o]"; KV-cache before the call is reused — [ReTool, §2.3.1-2.3.2](https://arxiv.org/abs/2504.11536)
- ARTIST: four segments <think>...</think>, <tool_name>...</tool_name> (e.g., <python>), <output>...</output>, <answer>...</answer>; "the policy model deciding at each step whether to reason internally or interact with an external resource" — [ARTIST, §2.3](https://arxiv.org/abs/2505.01441)
- ToolRL system prompt (verbatim): "<think> Your thoughts and reasoning </think> / <tool_call> / {"name": "Tool name", "parameters": {"Parameter name": "Parameter content", ...}} / ... / </tool_call> / <response> AI's final response </response>", with "Provide at least one of <tool_call> or <response>. Decide whether to use <tool_call> (possibly multiple times), <response>, or both" and "You can invoke multiple tool calls simultaneously"; tool feedback is appended in an <obs> field — [ToolRL, Fig. 4 and §3.2](https://arxiv.org/abs/2504.13958)
- Search-R1: <think>, <search>, <information> (top-3 passages appended), <answer>; the template opens "You must conduct reasoning inside <think> and </think> first every time you get new information"; action budget B = 4; a turn with neither search nor answer gets the message "My action is not correct. Let me rethink." (via fetched page) — [Search-R1, Table 1 / Algorithm 1](https://arxiv.org/abs/2503.09516)
- ToolkenGPT: the tool is a token. Reasoning mode predicts next token over V ∪ T (toolken embeddings W_τ concatenated to the LM head); once a toolken is predicted the model switches to "tool mode", where an in-context prompt shows calls in the syntax [tool](arguments); the result is inserted and reasoning mode resumes. Training target example: s = ("the", "area", "is", "2", "5", "6", "square", "feet") paired with s' = ("the", "area", "is", "[square]", "[N/A]", "[N/A]", "square", "feet") — [ToolkenGPT, §3.1-3.2 and Fig. 1](https://arxiv.org/abs/2305.11554)
- ToolkenGPT's ReAct baseline syntax for arithmetic: "... The cost is 50*3.2=<multiply>(50,3.2)=160"; "Once the syntax is detected during inference, the tool would be called" — [ToolkenGPT, §4.1](https://arxiv.org/abs/2305.11554)

How well models chain 2+ calls
- ToRA: "averaging 1.02 tool interaction rounds per problem" at zero-shot inference (max n rounds in training data = 3) — [ToRA, §3.4](https://arxiv.org/abs/2309.17452)
- ToolkenGPT FuncQA (13 tools): one-hop 0.73 (ReAct 0.57, CoT 0.20), multi-hop 0.15 (ReAct 0.06, CoT 0.03); GSM8K-XL (4 tools, 568 problems with magnified numbers): ToolkenGPT 0.33, ReAct 0.32, CoT 0.18, 0-shot ChatGPT 0.17; LLaMA-33B backbone. The multi-hop metric "allow[s] a margin of error of 0.1% to account for potential errors at each step of multi-hop reasoning". Toolken embeddings were trained "solely using one-hop synthetic data" (611 samples) yet "still manage to enhance performance in multi-hop problem contexts" — [ToolkenGPT, Table 2 and §4.1](https://arxiv.org/abs/2305.11554)
- Calc-X: GSM8K accuracy T5-L (700M) 17.0 → Calcformer-T5-L 34.2; T5-XL (3B) 19.2 → 39.6; Ape210K 19.0 → 53.1 (700M); Calcformers "surpass the accuracy of the baseline models 2-3 times", with 1.6 chained calculator calls per chain on average; the exception is AQuA-RAT, "due to the low average number of tool calls inside the AQuA-RAT training split, leading to inconsistent usage of the calculator on AQuA-RAT test questions" — [Calc-X, Table 1 and §5](https://arxiv.org/abs/2305.15017)
- ARTIST: >3 tool calls per AIME query after RL (vs 0.3 for the prompted base), response length up to 2x — [ARTIST, §5.1.2](https://arxiv.org/abs/2505.01441)
- ReTool: total correct code executions on the test set rose from 1k to 5k during RL and the model exhibits "code self-correction" after interpreter errors — [ReTool, §3.3](https://arxiv.org/abs/2504.11536)
- ReAct error analysis (50 correct + 50 incorrect trajectories each for ReAct and CoT, HotpotQA, PaLM-540B): ReAct failures are reasoning error 47%, search-result error 23%, hallucination 0%, label ambiguity 29%; CoT failures are reasoning error 16%, hallucination 56%, label ambiguity 28%; "one frequent error pattern specific to ReAct, in which the model repetitively generates the previous thoughts and actions" — [ReAct, Table 2 and §3.3](https://arxiv.org/abs/2210.03629)
- Toolformer cannot chain at all: "One such limitation is the inability of Toolformer to use tools in a chain (i.e., using the output of one tool as an input for another tool). This is due to the fact that API calls for each tool are generated independently; as a consequence, there are no examples of chained tool use in the finetuning dataset" — [Toolformer, §7](https://arxiv.org/abs/2302.04761)

Measurements closest to "copy the previous result correctly"
- PoT error analysis on 198 TAT-QA failures: 47% "value grounding error" ("the model fails to assign correct values to the variables relevant to the question"), 33% logic errors, 15% both, 5% actually correct; "the majority of the errors are value grounding errors, which is also common for other methods such as CoT" — [PoT, §3.4](https://arxiv.org/abs/2211.12588)
- ToRA failure modes on MATH (human-labelled random sample): reasoning error 38%, "Hallucination: Fabrication of numbers or answers" 5%, diagram understanding 21%, syntax error 9%, runtime error 9%, rationale-only error 3%, false negative 5% — [ToRA, Table 4](https://arxiv.org/abs/2309.17452)
- PAL vs CoT on GSM-HARD (one number per question replaced with a random integer of up to 7 digits): CoT (Codex) 65.6% → 23.1% in Table 1 (the text says 20.1%), PAL 72.0% → 61.2% (text: "remains stable at 61.5%"); replacing CoT prompts with large-number exemplars did not help — [PAL, §4.1 and Table 1](https://arxiv.org/abs/2211.10435)
- PAL prompt-format ablation: removing NL comments but keeping meaningful variable names slightly reduces accuracy; additionally replacing variable names with random characters "further decreases accuracy, and performs worse than CoT" — [PAL, §6 and Fig. 9](https://arxiv.org/abs/2211.10435)
- PoT's CoT+calculator ablation (post-hoc calculator applied to CoT text): "adding an external calculator only shows mild improvement over CoT on MWP datasets, much behind PoT ... due to its rigid post-processing step, which can lead to low recall in terms of calibrating the calculation results" (Codex: CoT 65.6 vs CoT+calc 65.4 vs PoT 71.6 on GSM8K) — [PoT, §3.2 and Table 2](https://arxiv.org/abs/2211.12588)

### Inferences
- (Inference) For a 64-token context, only the inline-interleaved family fits; the Calc-X / GSM8K / Toolformer pattern (expression, delimiter, tool writes the result token, model continues) is the direct analogue of "[op a b ->" + result token. Calc-X's example shows the real chaining burden: the number 27 produced by call 1 is re-typed by the model as an operand of calls 2 and 3. With single-token numbers the digit-level copy error disappears, but the "which number to copy" (value-grounding) error that dominates PoT's analysis remains, so a two-step eval should log whether the second call's operands equal the first call's result.
- (Inference) ToRA's 1.02 rounds/problem and ToRL's C = 1 default show that most published systems were effectively one-call-per-answer; genuine 2-call chaining is best evidenced by Calc-X (1.6 calls) and ToolkenGPT FuncQA-multi (0.15 vs 0.06), which are also the systems closest to the reader's scale.
- (Inference) PAL's variable-name ablation implies that what the model "copies" between steps is a named reference, not a number; an inline format can borrow this by letting the result token be referred to positionally (the CPU's last output) rather than re-typed, if the tool interface allows a "use previous result" operand.

### Gaps
- No paper reports a direct error rate for miscopying a tool result into the next call; all evidence is indirect (value-grounding and hallucination categories above).
- ToRA's and ReTool's trace examples are figures/listings not captured in text form here; the delimiters are confirmed from the method text (```output stop word; <code>/<interpreter>) but a full verbatim ToRA trajectory is not reproduced in these notes.

## Key question 3: What is known about transfer of tool-calling to unseen phrasings or problem templates: do models learn surface triggers for calls, or a general "I need to compute" decision? Any diagnostic studies?

### Takeaway
The one dedicated diagnostic ("Spurious Tool Use", 2026) shows that outcome-only RL does learn surface triggers: an injected, causally irrelevant cue raised unnecessary search calls on math problems by up to +39.2 points, shortcuts formed only for the tool the agent had actually learned to use well, and a per-call necessity reward removed them; other papers show the call decision is fragile (ToolRL's irrelevance detection collapses from 56% to 4.5% under a length reward) but also that trained tool use transfers across datasets and from one-hop to multi-hop (Search-R1, ToRA, ToolkenGPT, SMART), while Toolformer's model called the calculator on 97.9% of math-benchmark inputs, i.e., a near-unconditional trigger on that distribution.

### Cited Findings
- Spurious Tool Use setup: Qwen2.5-7B-Instruct, GRPO via VerlTool, 30 training steps, 1,000 training questions (500 Natural Questions needing web search + 500 DeepMath needing Python). A cue is injected into all examples of one subset: search-semantic cues into NQ ("Source: [WEB INDEX 742]" prepended; "[REFERENCE]" prepended; or the appended format instruction "Conclude your response by providing the final answer within <answer></answer> tags ..."), code-semantic cues into DeepMath ("# Cell [1] | kernel: python3 | status: idle", "#!/usr/bin/python3", "[CODE]"). Evaluation uses counterfactual pairs of the same question with and without the cue, ΔTool(Y−N) = π̂(T_s | x_c, a) − π̂(T_s | x_c), also on held-out 2Wiki and GSM8K — [Spurious Tool Use, §3 and Appendix](https://arxiv.org/abs/2609.16268)
- Results (Table 1, Δ in unnecessary search-call rate on math test sets): [WEB INDEX] cue +19.9 on DeepMath and +39.2 on GSM8K (search rate 40.1% with cue vs 0.9% without); <answer> cue +21.7 / +9.5; [REFERENCE] +7.7 / +20.1; no-cue controls within ±1.8. With the necessity reward: +0.0 / +0.3, +0.0 / +0.0, +0.2 / +0.1. Code-semantic cues produced no shortcut on factual tasks (ΔPy between −0.3 and +5.2) — [Spurious Tool Use, Tables 1-2](https://arxiv.org/abs/2609.16268)
- Mechanism: "shortcut formation is closely tied to task competence: a cue is more likely to become spuriously associated with a tool if the agent has learned to use that tool effectively on its intended task." NQ validation accuracy rose from ~45% to ~75% over 30 steps while DeepMath stayed flat at ~45-50%; "Across the conditions we test, shortcuts form only for the well-learned tool." A swapped-cue experiment shows semantic alignment also matters: code-semantic cues on the well-learned NQ task gave only ΔSearch ≤ +3.5 — [Spurious Tool Use, §5.3-5.4](https://arxiv.org/abs/2609.16268)
- The paper's framing of why this is hard to catch: "an unnecessary tool call ... need not cause task failure: an agent may invoke an unnecessary search, ignore the result, and still produce the correct answer. This means shortcuts can persist even under reward signals" — [Spurious Tool Use, §2.2](https://arxiv.org/abs/2609.16268)
- Toolformer: "across all benchmarks, for 97.9% of all examples the model decides to ask the calculator tool for help" (ASDiv / SVAMP / MAWPS: GPT-J 7.5 / 5.2 / 9.9; Toolformer with calls disabled 14.8 / 6.3 / 15.0; Toolformer 40.4 / 29.4 / 44.0; GPT-3 175B 14.0 / 10.0 / 19.8). Call frequency is a decoding knob: the <API> token is emitted if it is among the k most likely tokens; on LAMA T-REx the call rate goes from 40.3% (k = 1, greedy) to 98.1% (k = 10), on WebQS from 8.5% to 100% — [Toolformer, §4.2.2, §5, Table 9](https://arxiv.org/abs/2302.04761)
- ToolRL generalization: evaluated on "unseen programming languages and its ability to detect irrelevant tools, neither of which were explicitly included during RL training or in the dataset"; Qwen2.5-3B-Instruct trained with GRPO from the raw instruct model "consistently achieves highest performance"; qualitative case: given only find_critical_points for a slope question, the model writes "The given tool find_critical_points is not relevant to finding the slope of a line and cannot be used to solve this problem" and answers directly — [ToolRL, §4.3 and Table 4](https://arxiv.org/abs/2504.13958)
- ToolRL's BFCL "Irrelevance Detection" column (whether the model correctly refrains from calling) is the most volatile metric across reward variants: Qwen2.5-1.5B 56.44% (original) vs 4.52% (length reward) vs 16.44% (equal-max scale) vs 10.61% (two-stage) vs 57.20% (dynamic) — [ToolRL, Tables 5-6](https://arxiv.org/abs/2504.13958)
- SMART measures tool overuse as O = α·β (α = fraction of questions the model can answer without tools, β = fraction of those on which it still calls a tool); Llama-3.1-8B's overuse rate on GSM8K exceeds 50%. After SFT on SMART-ER, out-of-distribution results: Llama-3.1-8B on GSM8K 2.53 → 0.76 calls (accuracy 83.17 → 83.40), on MINTQA 4.03 → 1.06 calls (16.49 → 29.90); Mistral-7B on GSM8K 3.56 → 0.45 calls (55.34 → 58.98) (via fetched page) — [SMART (Qian et al. 2025)](https://arxiv.org/abs/2502.11435)
- Search-R1 (Qwen2.5-7B-base, PPO) trained on NQ + HotpotQA transfers to unseen datasets: TriviaQA 0.638, PopQA 0.457, 2Wiki 0.382, Musique 0.196, Bamboogle 0.432 (in-domain NQ 0.480, HotpotQA 0.433); average 0.431 vs RAG 0.304 and IRCoT 0.239 (via fetched page) — [Search-R1, Table 2](https://arxiv.org/abs/2503.09516)
- ToRA: "While rationale-based fine-tuning negatively affects out-of-distribution generalization, TORA displays superior generalization. For instance, WizardMath-70B underperforms the base model on TabMWP (49.8% vs. 57.5%), while TORA-70B effectively generalizes to this tabular reasoning task (74.0%)" — [ToRA, §3.4](https://arxiv.org/abs/2309.17452)
- ToolkenGPT: toolkens trained only on one-hop synthetic patterns generalize to multi-hop FuncQA (0.15 vs ReAct 0.06), "a degree of generalization of toolken embeddings"; ReAct with many tools "is susceptible to missing tool calls, making wrong tool calls, and predicting wrong arguments, especially for the tools not demonstrated in context" — [ToolkenGPT, §4.1](https://arxiv.org/abs/2305.11554)
- Calc-X: inconsistent calculator use at test time on AQuA-RAT is attributed to a low number of calls in that dataset's training split, i.e., the call decision tracked the training distribution's call density — [Calc-X, §5](https://arxiv.org/abs/2305.15017)
- OTC: after outcome-only RL, call counts vary by model and dataset ("3B model tends to use less tool calls compared with 7B model"), and the authors modified Search-R1's template "to tell the model that it only need to call tools when necessary" — [OTC, §4.1-4.2](https://arxiv.org/abs/2504.14870)
- The Qu et al. survey treats the call decision as an evaluation target: "it is crucial to assess whether LLMs correctly identify if a given query requires a external tool, measuring the accuracy of tool usage awareness", citing MetaTool and WTU-Eval as benchmarks that "assess whether LLMs can recognize the necessity of using tools"; it also notes that tuning-based approaches "heavily rely on the tools seen in the training set, and perform poorly with new tools not included in the dataset" (via fetched page) — [Qu et al. 2024 survey](https://arxiv.org/abs/2405.17935)

### Inferences
- (Inference) Mapping the Spurious-Tool-Use diagnostic onto the reader's data: the obvious cue is "two number tokens in the sentence". Counterfactual pairs are easy to construct (same numbers in a narrative sentence with no question vs with "now he has"; a question with words-only quantities; a question whose answer is in the text and needs no arithmetic). The paper's ΔTool(Y−N) is the right metric, and its finding that shortcuts form once the tool task is well learned predicts that a model which has mastered one-step calls will over-call on number-bearing narrative text unless no-call positions are rewarded.
- (Inference) Toolformer's 97.9% call rate and the k-threshold decoding show that, when evaluated only on problems that need the tool, "always call" is indistinguishable from "decide to call"; the reader's evaluation needs the no-call cases to be scored (ToolRL's Irrelevance Detection is the template).

### Gaps
- No study tests paraphrase or template robustness of the call decision for arithmetic specifically (e.g., "got 5 more" vs "found 5" vs "5 were given to him"); the Spurious Tool Use experiments vary metadata cues, not problem phrasing.
- No diagnostic was found for whether RL-trained math models call the tool on problems where the answer is stated in the text (no computation needed); AdaTIR's GSM8K numbers (calls 0.83 → 0.02) are the nearest evidence that outcome-only RL over-calls on easy problems.

## Key question 4: For a small model trained from scratch with synthetic data (not a pretrained LLM), what approaches are documented: supervised traces with tool outputs masked, REINFORCE / policy gradient with a verifiable reward, curriculum from one-step to two-step problems?

### Takeaway
No paper trains a from-scratch tiny GPT to call an external text-level tool on word problems with RL; the closest documented points are (a) a 4-layer, d=128 LLaMA trained from scratch that learns to parse "Add 3 and 4" into a (differentiable, internal) calculator with answer-only supervision (99.2% at 62 epochs), (b) Toolformer's finding that self-supervised tool use from web text only pays off at ~775M parameters, (c) Calcformers at 700M (fine-tuned T5) doubling accuracy with a calculator, (d) ToolkenGPT's embeddings-only training with [N/A]-masked result tokens, and (e) the RL recipes above, all of which (ReTool, ToRL, ARTIST, Search-R1) are SFT-cold-start + policy gradient with a verifiable final-answer reward and masked tool outputs.

### Cited Findings
- From-scratch tiny transformer with a calculator: "Our minimum viable transformer uses the LLaMA architecture with tiny scale parameters, and is trained from scratch ... a scaled LLaMA with a dimension of 128, 4 transformer heads, 2 key-value heads, and 4 transformer layers ... AdamW ... batch size of 32 and a learning rate of 1e-2." Trained on 45,151 natural-language one-step problems such as "Add 3 and 4" with a mod-128 lookup-table calculator, "Supervision is given only on answers, via cross-entropy. By 62 epochs, the model can use the calculator with 99.2% accuracy on the test set, and by 132 epochs the accuracy is 100%." The calculator is a differentiable module inside the network (operands and op are emitted as one-hot classifications), not a text-level external call, and tasks are one-step only — [Saldyt & Kambhampati 2024, §4.2](https://arxiv.org/abs/2407.04899)
- Toolformer scaling: GPT-2 models with 124M, 355M, 775M and 1.6B parameters plus GPT-J 6.7B; "the ability to leverage the provided tools only emerges at around 775M parameters: smaller models achieve similar performance both with and without tools", with the exception of the easy-to-use Wikipedia search; the gap between with- and without-API predictions "remains high" even for the biggest model — [Toolformer, §4.4 and Fig. 4](https://arxiv.org/abs/2302.04761)
- Calcformers: T5 and FLAN-T5 at 700M and 3B parameters fine-tuned "using teacher forcing and cross-entropy loss" on Calc-X targets, greedy decoding; 700M GSM8K 17.0 → 34.2, Ape210K 19.0 → 53.1, ASDiv-A 29.7 → 55.6 — [Calc-X, §5 and Table 1](https://arxiv.org/abs/2305.15017)
- ToolkenGPT trains only the toolken embedding matrix W_τ with the LLM frozen; objective L(W_τ) = Σ −log P(t'_i | t_<i) over positions where t'_i ≠ [N/A]; 5,054 GSM8K calculation-annotated examples (1,000 validation) for the 4 arithmetic toolkens; 611 synthetic one-hop samples for the 13 FuncQA tools — [ToolkenGPT, §3.2 and §4.1](https://arxiv.org/abs/2305.11554)
- Lee et al. train NanoGPT from random initialization ("six self-attention layers, six heads, and an embedding dimension of 384, resulting in approximately 10.6 million parameters", character-level) and show small transformers learn addition and related operations from scratch, with output format (e.g., reversed digits) and chain-of-thought-style intermediate steps changing sample efficiency — [Teaching Arithmetic to Small Transformers (Lee et al. 2023), §3](https://arxiv.org/abs/2307.03381)
- Supervised traces beat prompting at small scale (ReAct): finetuning PaLM-8B/62B on 3,000 ReAct trajectories with correct answers makes "PaLM-8B finetuned ReAct outperforming all PaLM-62B prompting methods, and PaLM-62B finetuned ReAct outperforming all 540B prompting methods", whereas finetuning Standard or CoT "essentially teaches models to memorize (potentially hallucinated) knowledge facts" — [ReAct, §3.3 and Fig. 3](https://arxiv.org/abs/2210.03629)
- Imitation + output-space shaping (ToRA): imitation learning minimizes −log P_M(r_{i+1} a_{i+1} | q, r_1 ... o_i) over the 16k GPT-4 trajectories (tool outputs are conditioned on, not predicted); shaping samples 64 trajectories per training question with nucleus sampling, keeps correct ones without tool-use errors, and repairs wrong ones by taking a prefix τ[:j] of lines and letting a teacher (CodeLLaMA-34B trained on ToRA-Corpus) complete it with greedy decoding; 233k valid + 69k corrected trajectories, of which up to 4 per problem are merged with ToRA-Corpus into 69k training annotations. Gains: +3.4 (GSM8k) and +4.0 (MATH) absolute on average, "with greater benefits for smaller models"; sampling alone +2.7, sampling+correction up to +4.5; MATH overall for ToRA-Code-7B 44.6 vs 40.2 without shaping vs 36.8 without rationales — [ToRA, §2.3, §3.5.2, Table 3](https://arxiv.org/abs/2309.17452)
- ToRA format ablation (same MATH data): tool-integrated format beats rationale-only by 29.0 and program-only by 6.7 points with LLaMA-2, and by 19.1 / 9.8 with GPT-4 — [ToRA, §3.5.1](https://arxiv.org/abs/2309.17452)
- RL recipe details relevant to a small-scale reimplementation: ReTool uses PPO, KL coefficient 0.0, lr 1e-6, two SFT epochs of cold start, max 16,384 tokens; the cold-start traces were built by rewriting text-only solutions, "replacing manual calculation steps that can benefit from code execution with the corresponding code snippets and their interpreter's execution results", then filtering by format and answer verification — [ReTool, §2.2-2.3](https://arxiv.org/abs/2504.11536)
- ARTIST uses GRPO with 8 rollouts per question at temperature 1.0 on 20,000 NuminaMath problems; Search-R1 uses PPO (GRPO converged faster but showed reward collapse); ToRL uses 28,740 questions and a per-response call limit; ToolRL uses GRPO on 4K (or 400) samples (via fetched pages for ARTIST training details, Search-R1 and ToRL) — [ARTIST](https://arxiv.org/abs/2505.01441), [Search-R1](https://arxiv.org/abs/2503.09516), [ToRL](https://arxiv.org/abs/2503.23383), [ToolRL](https://arxiv.org/abs/2504.13958)
- Self-RAG's supervised recipe for the call decision: a critic (Llama2-7B trained on 4k-20k GPT-4 labels per token type) inserts reflection tokens offline, including Retrieve ∈ {yes, no, continue}; the generator is then trained with ordinary next-token prediction on the augmented corpus with retrieved chunks masked, and at inference retrieves when P(Retrieve = yes) exceeds a threshold (0.2 by default) (via fetched page) — [Self-RAG](https://arxiv.org/abs/2310.11511)
- GSM8K's annotation generator is itself a from-data heuristic ("hard-coded logic and a finetuned language model"), "highly unlikely to generate any incorrect annotations, but ... not uncommon for it to ignore some lines that could be annotated" — [GSM8K, Appendix C](https://arxiv.org/abs/2110.14168)

### Inferences
- (Inference) The reader's model is at the scale where Toolformer found no benefit (124M-355M GPT-2 on web text), but that result is about discovering calls self-supervised from natural text; with synthetic data where every call is annotated and masked (ToolkenGPT/Calc-X style), the 4-layer d=128 from-scratch result of Saldyt & Kambhampati suggests the parsing-and-dispatch part is learnable at this size. The published evidence therefore favours: supervised traces first (tool result token masked from the loss, overridden at test time as in GSM8K), then REINFORCE with the result-check reward plus an efficiency term, matching the SFT-then-RL order used by ReTool/ToRL/ARTIST.
- (Inference) ToRA's "correct the prefix with a teacher" trick has a cheap synthetic analogue: when a sampled two-step trajectory fails after the first call, keep the prefix up to the first correct call and complete it with the generator's ground-truth continuation, giving on-policy-looking multi-step data without a large teacher.
- (Inference) A one-step → two-step curriculum is not documented anywhere in these sources; the only related evidence is ToolkenGPT's one-hop-only training transferring partially to multi-hop and ToRL's explicit call limit C, which caps (rather than schedules) the number of calls.

### Gaps
- No source trains a sub-100M from-scratch model to emit external tool calls on word problems with RL; the from-scratch result uses an internal differentiable calculator and one-step inputs only.
- No source documents a curriculum from one-step to two-step tool problems.
- Toolformer's GPT-2 scaling figure gives only "similar performance with and without tools" below 775M; exact per-size numbers are in a figure not captured here.

## Key question 5: Methods for making the call decision robust: adding negative examples (text with numbers where no call is needed), balancing call vs no-call positions, explicit "no tool needed" tokens.

### Takeaway
Documented techniques are: per-step labels of "tool needed / not needed" in SFT data (SMART-ER, with [[Reasoning]] vs [[Search]] prefixes in one variant); an explicit learned no-retrieve token (Self-RAG's Retrieve = no/continue); explicit "no tool applies" instructions and metrics (Nemotron's "If none of the function can be used, point it out", BFCL irrelevance detection as used by ToolRL); tool-free rollouts in the RL group so that 0-call solutions compete (EAPO); necessity-judged per-call penalties (Spurious Tool Use); difficulty-gated penalties (AdaTIR); and Toolformer's loss-based filter, which implicitly creates no-call positions by discarding calls that do not reduce loss. No source reports an explicit experiment on balancing the number of call vs no-call positions.

### Cited Findings
- SMART-ER: each query is split into subgoals with labels A(s_i) = 1 (needs a tool) or 0 (parametric knowledge suffices), annotated by GPT-4o using the ground truth as a heuristic; parametric steps are r_i = (k_i), tool steps are r_i = (p_i, o_i) (parameters and output), and each step carries a justification j_i for why a tool is or is not needed; the main format has no literal "no tool" token, but the confidence experiment (Appendix C.5) prepends [[Reasoning]] for internal steps, [[Search]] and [[AskUser]] for tool steps. SFT (LoRA rank 16, 3 epochs) on this data "reduces tool use by 24% while improving performance by over 37%" (Llama-3.1-8B Math: calls 1.93 → 0.88, accuracy 51.00 → 54.75; Mistral-7B Math: 3.90 → 0.60, 13.25 → 22.75) (via fetched page) — [SMART](https://arxiv.org/abs/2502.11435)
- Self-RAG: the Retrieve reflection token takes values {yes, no, continue} and "Decides when to retrieve"; retrieval is triggered when the normalized probability of Retrieve = yes exceeds a threshold, and "Lowering the threshold makes retrieval more frequent" (via fetched page) — [Self-RAG, Table 1 and §3.3](https://arxiv.org/abs/2310.11511)
- Nemotron Tool-N1's template includes the instruction "If none of the function can be used, point it out", but the paper does not evaluate abstention or over-calling; its reward only scores matches against a ground-truth call (via fetched page) — [Nemotron Tool-N1](https://arxiv.org/abs/2505.00024)
- ToolRL's template forces an explicit choice at every turn ("Provide at least one of <tool_call> or <response>. Decide whether to use <tool_call> (possibly multiple times), <response>, or both") and the paper reports BFCL "Relevance Detection" and "Irrelevance Detection" separately; the qualitative examples show the model "proactively rejects inappropriate tool use—first by clarifying ambiguous intent, and second by opting to answer directly without tools" — [ToolRL, Fig. 4, §4.3, Table 5](https://arxiv.org/abs/2504.13958)
- EAPO generates at least n = 2 of the M = 16 rollouts per query with tools disabled; tool-free trajectories receive the efficiency coefficient ε = 1 (they are treated as achieving c_min), so a correct no-call solution is the reference point against which tool-using solutions are discounted (via fetched page) — [EAPO](https://arxiv.org/abs/2606.02132)
- OTC: a template change telling the model it "only need to call tools when necessary" was used alongside the reward (Search-R1 setting), and in the GRPO variant the group's minimum call count (including 0) defines the target — [OTC, §4.1 and §3](https://arxiv.org/abs/2504.14870)
- AdaTIR applies its penalty only when the rollout is correct and the query is easy (φ_q < 0.8), and reports a qualitative "cognitive offloading" case where the baseline reasons to the answer "8 cm" internally and then writes code "to verify"; it cuts GSM8K calls from 0.83 to 0.02 per problem while accuracy rises 91.0 → 92.8 (via fetched page) — [AdaTIR](https://arxiv.org/abs/2601.14696)
- Spurious Tool Use: the necessity judge treats "trivial arithmetic, formatting" calls as unnecessary and the penalty is applied only to unnecessary calls; this eliminated cue-driven calls (Δ ≤ +0.3) without accuracy loss — [Spurious Tool Use, §4.1, Table 1](https://arxiv.org/abs/2609.16268)
- Toolformer: calls are kept only when they reduce the loss on subsequent tokens by τ_f, so positions where the model already predicts the continuation well (and all positions in the ~99% of texts without useful calls) become implicit no-call examples; the authors chose thresholds per tool "to ensure a sufficiently larger number of examples"; the model's own tendency to call is then controlled by the <API>-token decoding threshold k — [Toolformer, §2-3, §5](https://arxiv.org/abs/2302.04761)
- Toolformer heuristic pre-filter for calculator data: candidate texts must "contain at least three numbers within a window", i.e., the training signal for the calculator came only from number-dense text, with no explicit negatives from number-bearing prose — [Toolformer, Appendix A](https://arxiv.org/abs/2302.04761)
- PoT zero-shot: "a caveat is that LLM can fall back to generating a reasoning chain in comments rather than in the program. Therefore, we propose to suppress '#' token logits to encourage it to generate programs" — a decoding-time intervention on the call-vs-text decision — [PoT, §2.2](https://arxiv.org/abs/2211.12588)
- ReAct's "CoT-SC → ReAct" rule: "when the majority answer among n CoT-SC samples occurs less than n/2 times (i.e. internal knowledge might not support the task confidently), back off to ReAct", giving 34.2 EM on HotpotQA vs 29.4 for CoT and 27.4 for ReAct alone — a confidence-based call decision — [ReAct, §3.2-3.3, Table 1](https://arxiv.org/abs/2210.03629)
- Calc-X: injected calls are only placed where the annotator wrote "expression = number" and the calculator agrees; the authors propose filtering to samples with at least three calculator calls "for applications with high priority of recall in the injected gadget calls", i.e., the call density of training data was deliberately tuned — [Calc-X, §4](https://arxiv.org/abs/2305.15017)

### Inferences
- (Inference) For the reader's synthetic data, the cheapest robustness measures implied by these sources are: (1) include number-bearing narrative sentences with no question and sentences whose question is answered by a stated number, labelled as no-call (SMART-ER's A(s_i) = 0 analogue); (2) give the model an explicit "no-call" option at each decision point rather than only the absence of a call (ToolRL's forced <tool_call>-or-<response>, Self-RAG's Retrieve = no); (3) in REINFORCE, sample some rollouts with the gate forced closed so 0-call solutions are in the comparison group (EAPO); (4) report an irrelevance-detection accuracy alongside answer accuracy (ToolRL), since that metric collapsed under seemingly innocuous reward changes.
- (Inference) Because the reader's generator knows which sentences need arithmetic, the Spurious-Tool-Use necessity label is available exactly (no LLM judge needed), and the SMART overuse rate O = α·β can be computed per checkpoint from a tool-disabled eval pass.

### Gaps
- No source reports an experiment on the ratio of call to no-call positions in training data, or on whether balancing that ratio changes the learned call rate; Calc-X's AQuA-RAT observation (low call density → inconsistent calling) is the only related evidence.
- No source evaluates an explicit "no tool needed" token for arithmetic specifically; Self-RAG's Retrieve = no token is for retrieval, and SMART's [[Reasoning]] prefix appears only in an appendix confidence experiment without a separate ablation.
