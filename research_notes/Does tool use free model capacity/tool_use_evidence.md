# Does tool use free model capacity? What the tool-augmented LM literature actually measured

Scope note for the report writer: every quantitative result below comes from models of 110M parameters (BERT-base) up to 280B. Nothing published that I could find trains a tool-using model anywhere near the user's 1.4M-parameter scale. "Freed capacity" is a stated hypothesis in two surveys; it has never been measured as such. The closest well-measured analogues are (a) Toolformer's "no cost in perplexity" table at 6.7B, and (b) the retrieval literature (RETRO, kNN-LM), where external memory lets a smaller model match a larger one on perplexity. Numbers, model sizes and dates are given for each.

## 1. Toolformer (Schick et al., Feb 2023): what did it report about LM perplexity after tool training?

### Takeaway
Toolformer (GPT-J, 6.7B) measured perplexity only with API calls disabled and found no change versus a baseline fine-tuned on the same CCNet subset without calls (WikiText 10.3 vs 10.3; CCNet 10.5 vs 10.5). The claim is "no cost", not improvement; no perplexity with calls enabled is reported because marginalizing over possible calls is intractable.

### Cited Findings
- Language-modeling table (Table 8, perplexity, lower is better): GPT-J 9.9 (WikiText) / 10.6 (CCNet); GPT-J + CC (fine-tuned on the CCNet subset without API calls) 10.3 / 10.5; Toolformer (disabled) 10.3 / 10.5. No "Toolformer (enabled)" row. — [Toolformer, arXiv:2302.04761](https://arxiv.org/abs/2302.04761)
- Exact claim: "Most importantly, however, training on C* (our dataset annotated with API calls) does not lead to an increase in perplexity compared to training on C when API calls are disabled at inference time." Table caption: "Adding API calls comes without a cost in terms of perplexity for language modeling without any API calls." — [Toolformer](https://arxiv.org/abs/2302.04761)
- Why no enabled-calls perplexity: computing it would require marginalizing over all potential API calls, which the paper says "is intractable." — [Toolformer](https://arxiv.org/abs/2302.04761)
- Base model GPT-J (6.7B); fine-tuning data is a CCNet subset; training uses "a standard language modeling objective"; batch 128, lr 1e-5, sequence length 1,024, up to 2k steps, best checkpoint chosen by dev-set perplexity every 500 steps. The paper text does not say whether API-result tokens are masked from the loss. — [Toolformer](https://arxiv.org/abs/2302.04761)
- How little calculator data there was: at the filtering threshold tau_f = 1.0 the augmented dataset contains 994 calculator examples, versus 18,526 QA, 60,974 Wikipedia search, 20,587 calendar, 1,034 machine translation. The calculator heuristic only considers texts with at least three numbers. Stated limitation: "Depending on the tool, our method is also very sample-inefficient." — [Toolformer](https://arxiv.org/abs/2302.04761)
- Scale: tested GPT-2 124M, 355M, 775M, 1.6B plus GPT-J 6.7B (QA, calculator, Wikipedia search only); "the ability to leverage the provided tools only emerges at around 775M parameters," with Wikipedia search as an exception because that API is "comparably easy to use." Per-size numbers are only in Figure 4 (a plot), not in text. — [Toolformer](https://arxiv.org/abs/2302.04761)
- Internal math skill with the tool switched off did not degrade; it improved: Toolformer (disabled) ASDiv 14.8 / SVAMP 6.3 / MAWPS 15.0 versus GPT-J + CC 9.6 / 5.0 / 9.3 and plain GPT-J 7.5 / 5.2 / 9.9. With calls enabled: 40.4 / 29.4 / 44.0, versus GPT-3 (175B) 14.0 / 10.0 / 19.8 and OPT (66B) 6.0 / 4.9 / 7.9. — [Toolformer](https://arxiv.org/abs/2302.04761)
- Same pattern on LAMA (SQuAD / Google-RE / T-REx): GPT-J 17.8 / 4.9 / 31.9; GPT-J + CC 19.2 / 5.6 / 33.2; Toolformer (disabled) 22.1 / 6.3 / 34.9; Toolformer 33.8 / 11.5 / 53.5; GPT-3 175B 26.8 / 7.0 / 39.8. — [Toolformer](https://arxiv.org/abs/2302.04761)
- Where the small tool model does not catch the big one: open QA (WebQS / NQ / TriviaQA) Toolformer 26.3 / 17.7 / 48.8 vs GPT-3 29.0 / 22.6 / 65.9; the paper concedes "Toolformer still lags behind the much larger GPT-3 (175B) model." — [Toolformer](https://arxiv.org/abs/2302.04761)
- Other stated limitations: tools cannot be chained; no interactive tool use; sensitivity to input wording when deciding whether to call; cost of a call is not considered. — [Toolformer](https://arxiv.org/abs/2302.04761)
- Secondary write-ups reproduce Table 8 and make the same reading: the like-for-like comparison is Toolformer-disabled against the CCNet-fine-tuned baseline (identical), and the move from 9.9 to 10.3 on WikiText is attributable to the fine-tuning itself. — [aiwiki summary](https://www.aiwiki.ai/wiki/toolformer)

### Inferences
- The only matched-data perplexity measurement in the tool-use literature is this table, and it reports equality at 0.1 resolution with no seeds or confidence intervals. It is evidence that tool training does not hurt general text modeling at 6.7B; it is not evidence of freed capacity, and the authors never claim improvement.
- The 0.4-point worsening on WikiText (9.9 to 10.3) is a cost of fine-tuning on CCNet at all (the no-tool fine-tuned baseline pays it too), i.e., distribution drift, not tool use.
- The "disabled" rows are the closest thing to a "use it or lose it" test: at 6.7B, learning to call a calculator did not erode the model's own arithmetic; the disabled model was better than the matched baseline. Caveat: C* is not the same text as C (it contains inserted call strings and was filtered for calls that reduce loss), so the comparison is matched in source corpus but not in exact tokens.
- The 775M emergence threshold is for self-supervised discovery of when to call, with 1,024-token contexts and under 1k calculator examples. It does not transfer to a setting where calls are densely and explicitly supervised; TALM (220M) and Calcformer (700M) learned calculator calls from supervised data (see Section 2).

### Gaps
- No perplexity with calls enabled; no matched-compute or matched-token comparison (C* and C differ in token count).
- No per-size perplexity for the GPT-2 variants; the scaling result is a figure only.
- I found no published re-analysis or replication of the perplexity table; secondary blogs only restate it.

## 2. Calculator-augmented training (Cobbe 2021, TALM 2022, PAL 2022, Calc-X 2023, ToolkenGPT 2023, Lee et al. 2023, SyReLM 2023): did anyone compare language quality at matched size, or see internal arithmetic degrade?

### Takeaway
No calculator-tool paper measured language quality, perplexity, or general ability of the tool model against a matched non-tool model, and none reported internal arithmetic degrading; the only "tool switched off" numbers (Toolformer, SyReLM) show the tool-trained model equal or better. Two of the training recipes (Cobbe, Calc-X) keep the calculator's output tokens in the loss, so those models are still trained to compute and could not show freed capacity even in principle.

### Cited Findings
- Cobbe et al. (GSM8K, Oct 2021; GPT-3 family 3B to 175B): "we train all models to use a calculator by injecting calculation annotations into the training set" and "At test time, a calculator will override sampling when the model chooses to use these annotations." Training treats calculator output like any other text: "During training, there is no special distinction between the annotated tokens and the rest of the solution: they are all just tokens." On internal arithmetic: "Our models frequently fail to accurately perform calculations. Although larger models make fewer arithmetic mistakes than smaller models, this remains a common source of errors." The only calculator-related number in the text: "Fixing the calculator improves verification test performance by about 1% when using the full GSM8K training set." No with/without-calculator ablation appears in the extracted text. — [Cobbe et al., arXiv:2110.14168](https://arxiv.org/abs/2110.14168)
- TALM (Parisi, Zhao, Fiedel, May 2022; T5 base 220M, large, XL 3B): on Natural Questions "even the 220M base TALM outperforms 3B XL LM"; on MathQA TALM "significantly outperforms a non-augmented LM"; conclusion: tool augmentation with self-play "enables smaller models to outperform larger non-augmented LMs." Bootstrapped from "150 tool demonstrations" (NQ) and about 2k MathQA examples. No perplexity or general-capability evaluation after tool training; all results are figures, no numeric tables. — [TALM, arXiv:2205.12255](https://arxiv.org/abs/2205.12255)
- Calc-X / Calcformers (Kadlcik et al., May 2023; T5-L 700M, T5-XL 3B, Flan-T5-XL 3B), Table 1 (% correct): T5-L no-calc GSM8K 17.0, Ape210K 19.0, MAWPS 11.2, SVAMP 18.2, ASDiv-A 29.7, AQuA-RAT 26.6; Calcformer-T5-L 34.2 / 53.1 / 39.4 / 34.4 / 55.6 / 27.2. T5-XL no-calc 19.2 / 20.8 / 16.0 / 24.7 / 37.0 / 33.5; Calcformer-T5-XL 39.6 / 53.8 / 49.0 / 44.7 / 66.8 / 33.5. Flan-XL no-calc 24.2 / 22.9 / 15.8 / 24.0 / 38.7 / 20.8; Calcformer-Flan-XL 39.4 / 53.4 / 47.1 / 46.7 / 72.5 / 31.2. Summary: "Calcformers surpass the accuracy of the baseline models 2-3 times, with the exception of the AQuA-RAT dataset." Training: "We applied standard sequence-to-sequence training with cross-entropy loss on all tokens" (calculator output is inside the target text). Only metric is final-answer accuracy; no perplexity, language quality, or forgetting measured. — [Calc-X, arXiv:2305.15017](https://arxiv.org/abs/2305.15017)
- ToolkenGPT (Hao et al., May 2023; LLaMA): "Our framework keeps the original LLM parameters frozen"; only tool-token embeddings are learned; stated motivation against fine-tuning: "LLM fine-tuning is costly and these tuned LLMs struggle to generalize to emergent or updated tools." Forgetting is therefore avoided by construction, not measured. — [ToolkenGPT, arXiv:2305.11554](https://arxiv.org/abs/2305.11554)
- PAL (Gao et al., Nov 2022; prompting only, no training; Codex): GSM8K PAL 72.0 vs CoT-Codex 65.6 vs CoT PaLM-540B 56.9 vs Minerva-540B 58.8; GSM-hard PAL 61.2 vs CoT 23.1. The gain is from the interpreter, not the code format: a code-format prompt without execution "resulted in a 23.2 solve rate on gsm8k, much lower than PaL (72.0)", and "the main benefit of PaL comes from the synergy with the interpreter." Framing: "offloading the calculation and some of the reasoning to a Python interpreter, which is correct by construction"; "decomposing the natural language problem into runnable steps remains the only learning task for the LLM." Weak models are hurt: text-davinci-001 CoT 26.5 vs PAL 8.6; text-davinci-002 46.9 vs 65.8; text-davinci-003 65.3 vs 69.8. — [PAL, arXiv:2211.10435](https://arxiv.org/abs/2211.10435)
- Teaching Arithmetic to Small Transformers (Lee et al., Jul 2023; NanoGPT 10.6M, 6 layers, 6 heads, 384-dim, scaled up to GPT-2-size): no tools anywhere in the paper. Plain-format addition "plateaus at slightly over 85% even with 10,000 samples"; "Simplified Scratchpad data achieves 100% accuracy with only 2000 samples"; detailed scratchpad "achieves perfect addition with just 1000 samples." Text mixing (1,115,394 Shakespeare tokens plus 10,000 addition examples = 120,027 tokens): "text prompts negatively influence performance when the model is trained only on addition"; Figure 25 caption: "the training perplexity on Shakespeare also tends to increase, which indicates some overfitting" but the model "still outputs 'reasonable' text when prompted with shakespeare text." Numeric perplexity values are only in figures. GPT-3 fine-tuning (Davinci/Curie/Ada, 1,000 examples, 4 epochs): detailed-scratchpad addition 99.5 / 99.7 / 99.8%, but no perplexity or general-ability measurement. Caveat from the authors: "it remains uncertain if all our findings can be generalized to the scale of LLMs being used in practice today." — [Lee et al., arXiv:2307.03381](https://arxiv.org/abs/2307.03381)
- The reverse experiment (teach arithmetic internally, check that language survives) exists: GenBERT (Geva, Gupta, Berant, Apr 2020; BERT-base) pre-trained on 1M synthetic numeric and 2.5M synthetic textual examples. SQuAD v1 dev: BERT 81.1 EM / 88.6 F1; GenBERT+ND+TD 81.3 / 88.6, "almost identical to the original BERT"; DROP dev rose from 46.1 / 49.3 to 68.8 / 72.3. Dropping the MLM (language) loss during numeric pre-training cost 3 EM on SQuAD, "highlighting the importance of using the MLM loss." — [GenBERT, arXiv:2004.04487](https://arxiv.org/abs/2004.04487)
- SyReLM (Dutta et al., Dec 2023; Vicuna-13B and GPT-J-6B, frozen, LoRA r=4 / r=16, trained with policy gradient against a symbolic solver), Table 1: Vicuna-13B SyReLM SVAMP 56.65 / MultiArith 59 / GSM8K 35.2 vs the same model fine-tuned with the LM objective and run without the solver (LMFT) 42.5 / 48.3 / 29.8, vs PAL 53.7 / 49.4 / 27.5; GPT-J SyReLM 40.1 / 53.16 / 3.50 vs GPT-J LMFT 31.6 / 42.16 / 2.2; Toolformer (GPT-J) SVAMP 29.4; GPT-3.5 8-shot 64.8 / 34.0 / 15.1. The authors give "the LM will lose its generic language modeling ability" as the reason to avoid full fine-tuning, but measure no perplexity or general benchmark. — [SyReLM, arXiv:2312.05571](https://arxiv.org/abs/2312.05571)
- Giving a calculator to a model that can already compute can hurt (prompting, not training): Qin et al. Table 1, calculator accuracy, text-davinci-003 no tool 85.3 / zero-shot tool 81.6 / few-shot tool 92.5; ChatGPT 91.7 / 74.1 / 92.5; "utilizing tools with zero-shot prompting could sometimes lead to worse performance." — [Qin et al., arXiv:2304.08354](https://arxiv.org/abs/2304.08354)
- A counterpoint to offloading at all: a secondary summary of MathGLM reports a 2B model doing multi-digit arithmetic without a calculator and argues LLM arithmetic weakness is largely a data-coverage problem (secondary source, not verified against the paper). — [dair.ai summary](https://academy.dair.ai/papers/gpt-solves-math-problems-without-a-calculator)

### Inferences
- In Cobbe's and Calc-X's recipes the model is still supervised on the answer digits, so there is no mechanism by which capacity could be freed; the calculator only fixes errors at test time. The user's design (machine tokens excluded from the loss) is the version that could show freed capacity, and I found no published precedent for it with a matched no-call control and a language metric.
- Toolformer's and SyReLM's tool-off rows both point the same way: training a model to call a solver did not make it worse at arithmetic on its own at 6B to 13B; if anything the curated tool data helped. No paper shows "use it or lose it."
- PAL's text-davinci-001 result (CoT 26.5 vs PAL 8.6) and Toolformer's 775M threshold both say that for weak models the cost of producing a correct call can exceed the benefit of the tool; at 1.4M parameters the user's model is paying a syntax/decision cost that the big-model papers do not have to think about.
- GenBERT is the cleanest evidence that a BERT-size model can absorb a large synthetic arithmetic curriculum with essentially zero cost to language ability, provided language loss is kept in the mix; this bounds how much "capacity" internal arithmetic plausibly consumes at 110M, and suggests the no-calls baseline is not obviously handicapped at the user's scale either.

### Gaps
- Cobbe et al.: no trained-with vs trained-without calculator ablation found in the text (if one exists it is in a figure I could not extract from the PDF).
- ToolkenGPT: I could not extract the GSM8K-XL / FuncQA result tables (ar5iv render truncated; PDF not parseable here).
- Program-of-Thoughts (Chen et al. 2022) and Pre-Calc (SemEval 2024, calculator pretraining for BERT/RoBERTa/Flan-T5) were not fetched; neither, from what I saw, reports language-quality or forgetting metrics.
- No paper trains a calculator-calling model below ~200M parameters with a matched no-tool control, and none reports text perplexity for such a comparison.

## 3. Surveys (Mialon et al. Feb 2023; Qin et al. Apr 2023, v3 Aug 2024): do they frame "offloading frees capacity" as motivation or as measured effect?

### Takeaway
Both surveys state offloading as a motivation and a hypothesis ("tool-augmented LMs may have better scaling laws and thus yield smaller models retaining the capabilities of their largest counterpart"), never as a measured effect, and Mialon et al. add the caveat that tool-augmented models "might actually lose the ability to assign a probability to the next token."

### Cited Findings
- Mialon et al., Sec. 1.1 Motivation: "massive scale is required to store knowledge that is not present in the context"; "it is possible to match certain capabilities of some of the largest LMs while having less parameters." — [Augmented Language Models survey, arXiv:2302.07842](https://arxiv.org/abs/2302.07842)
- Mialon et al., Sec. 3.2: "knowledge in the form of natural language can be offloaded completely from the LM by retrieving from an external knowledge source." — [Mialon et al.](https://arxiv.org/abs/2302.07842)
- Mialon et al., Sec. 5 Discussion, "Generalizing the non-parametric framework": tool use generalizes retrieval-based non-parametric models; delegating rarely needed knowledge and abilities to external tools means the model need not store them in weights, so "tool-augmented LMs may have better scaling laws and thus yield smaller models retaining the capabilities of their largest counterpart." Framed as a possibility, with no supporting measurement. — [Mialon et al.](https://arxiv.org/abs/2302.07842)
- Mialon et al., Sec. 5, "Moving away from language modeling": "tool-augmented LMs might actually lose the ability to assign a probability to the next token," because the probability would have to account for every possible tool call, which may be intractable; this is why they propose the term Augmented Language Models. — [Mialon et al.](https://arxiv.org/abs/2302.07842)
- Mialon et al., Sec. 4.1 on fine-tuning after pre-training: "A potential risk of finetuning after the pre-training phase is that the LM might deviate far from the original distribution"; mitigation discussed is mixing pre-training data with the reasoning/tool demonstrations. — [Mialon et al.](https://arxiv.org/abs/2302.07842)
- Mialon et al. Sec. 3.2.1 on retrieval: "These proposals close the performance gap compared to larger LMs that use significantly more parameters"; RETRO "obtaining comparable performance to GPT3 on different downstream tasks." — [Mialon et al.](https://arxiv.org/abs/2302.07842)
- Qin et al.: "it is necessary to augment foundation models with real-time tool execution to mitigate limitations in memorization"; "a significant proportion of the memorization burden can be offloaded to the search engine and database systems." Abstract: existing work is recapitulated "into tool-augmented and tool-oriented learning"; experiments cover "18 representative tools." — [Tool Learning with Foundation Models, arXiv:2304.08354](https://arxiv.org/abs/2304.08354)
- Qin et al. Sec. 5.7, "Striking a Balance between Internalized Capabilities and External Tools": "foundation models have increasingly displayed the ability to internalize and perform many AI tasks"; "The open question is to determine the optimal balance between internalized capabilities and external tool reliance." — [Qin et al.](https://arxiv.org/abs/2304.08354)
- Neither survey discusses catastrophic forgetting from tool training, nor cites any measurement of parameter savings from tool use; Qin et al. mention smaller models only in the context of distillation for privacy. — [Mialon et al.](https://arxiv.org/abs/2302.07842); [Qin et al.](https://arxiv.org/abs/2304.08354)

### Inferences
- The "freed capacity" idea is in the literature as an explicit conjecture (Mialon et al. Sec. 5), so the user's hypothesis is not idiosyncratic; what is missing is any experiment designed to test it. A clean small-scale test would be a genuine contribution.
- Mialon's "lose the ability to assign a probability" point is relevant to how the user evaluates: perplexity of a tool model is only well defined on text where no call would fire (the user's story-only perplexity is the right quantity, and matches Toolformer's calls-disabled protocol).

### Gaps
- Neither survey quantifies capacity, parameter savings, or forgetting; later surveys were not checked.

## 4. Does anyone show "a smaller model with a tool matches a larger model without it", with numbers?

### Takeaway
Yes, repeatedly, but always on the tool's own task and never on general language quality: Toolformer 6.7B beats GPT-3 175B on math word problems and LAMA; TALM 220M beats a 3B T5 on NQ; Calcformer-T5-L 700M beats T5-XL 3B without calculator on 5 of 6 math sets; SyReLM Vicuna-13B beats 8-shot GPT-3.5 on GSM8K and MultiArith but not SVAMP.

### Cited Findings
- Toolformer (6.7B) vs GPT-3 (175B): ASDiv 40.4 vs 14.0; SVAMP 29.4 vs 10.0; MAWPS 44.0 vs 19.8; LAMA T-REx 53.5 vs 39.8; but open-domain QA TriviaQA 48.8 vs 65.9 (loses). — [Toolformer](https://arxiv.org/abs/2302.04761)
- TALM: "even the 220M base TALM outperforms 3B XL LM" on NQ; "enables smaller models to outperform larger non-augmented LMs." — [TALM](https://arxiv.org/abs/2205.12255)
- Calcformer-T5-L (700M) vs T5-XL (3B, no calculator): GSM8K 34.2 vs 19.2; Ape210K 53.1 vs 20.8; MAWPS 39.4 vs 16.0; SVAMP 34.4 vs 24.7; ASDiv-A 55.6 vs 37.0; AQuA-RAT 27.2 vs 33.5 (loses). The paper does not state this comparison; it is read off Table 1. — [Calc-X](https://arxiv.org/abs/2305.15017)
- SyReLM: "On SVAMP and GSM8K datasets, SyReLM makes Vicuna 13B perform comparable to GPT-3.5 (standard 8-shot prompting)"; actual numbers SVAMP 56.65 vs 64.8, GSM8K 35.2 vs 15.1, MultiArith 59 vs 34.0. — [SyReLM](https://arxiv.org/abs/2312.05571)
- PAL (Codex) 72.0 on GSM8K vs PaLM-540B chain-of-thought 56.9, "surpassing PaLM-540b which uses chain-of-thought by absolute 15% top-1" (model sizes of Codex not public). — [PAL](https://arxiv.org/abs/2211.10435)
- A student project reports a 0.5B Qwen-2.5 with a calculator scoring 0.314 on 1,000 held-out Countdown problems and claims near-state-of-the-art at a fraction of the compute; preliminary, unreviewed. — [CS224R report](https://cs224r.stanford.edu/projects/pdfs/CS224R_Final_Report__1_%20(2).pdf)

### Inferences
- These are "parameter efficiency on the tool task" results: the tool supplies a capability, and the comparison model is bigger but tool-less. None of them holds training data or compute equal and then asks whether the tool model is better at something unrelated to the tool. That is the measurement the user's hypothesis needs, and it is absent.
- The pattern of where the small tool model still loses (open QA for Toolformer, AQuA-RAT for Calcformer, SVAMP for SyReLM) is consistent with tools adding a skill rather than freeing general capacity.

### Gaps
- No paper reports general benchmarks (perplexity, MMLU-style, or generation quality) for the small-tool vs large-no-tool pair.

## 5. Retrieval-augmented LMs (RETRO, kNN-LM): does offloading memorization let a smaller model match a larger one on perplexity, and what are the caveats?

### Takeaway
Yes, and it is the best-measured analogue: RETRO 7.5B matches or beats Jurassic-1 178B and Gopher 280B on most Pile subsets ("25x fewer parameters"), with gains equivalent to "non-retrieval models with 10x more parameters on certain datasets"; kNN-LM shows a 247M model trained on 100M tokens plus a 3B-token datastore (13.73 ppl) beats the same model trained on all 3B tokens (15.17). Caveats: gains are dataset-dependent, partly from leakage, come from the external memory being present at inference, and RETRO-fit shows the base weights are unchanged when retrieval is off.

### Cited Findings
- RETRO (Borgeaud et al., Dec 2021): "obtains comparable performance to GPT-3 and Jurassic-1 on the Pile, despite using 25x fewer parameters"; comparison models are "the 178B parameter Jurrasic-1 ... model and the 280B parameter Gopher"; "Overall, Retro 7.5B outperforms Jurassic-1 and Gopher on a majority of the test sets," but not on "dm_mathematics and ubuntu_irc." Model pairs: baselines 132M / 368M / 1.3B / 7.0B vs RETRO 172M / 425M / 1,451M / 7,532M. — [RETRO, arXiv:2112.04426](https://arxiv.org/abs/2112.04426)
- "on all datasets, Retro outperforms the baseline at all model sizes"; "The performance is dataset dependent, with the largest gains on Wikitext103 and C4"; "The smallest gains are for Curation Corpus." Gains "correspond to non-retrieval models with 10x more parameters on certain datasets." — [RETRO](https://arxiv.org/abs/2112.04426)
- Wikitext103 test perplexity: baseline Transformer 22.96; RETRO retrieving from Wikipedia 18.97; from C4 10.23; from full MassiveText 3.92, the last "partly due to partial overlap with Wikitext103 not caught by our deduplication." — [RETRO](https://arxiv.org/abs/2112.04426)
- Leakage: "only a modest fraction of the gains obtained by Retro are due to test set leakage"; "Retro models exploit leakage more strongly than baseline models"; "Retro outperforms baseline models at all leakage levels, down to alpha = 12.5%." — [RETRO](https://arxiv.org/abs/2112.04426)
- RETRO-fit (adding retrieval to a pretrained model): "requiring only 6 million sequences (3% of the pre-training sequences that we used)"; "by only training the new weights we ensure that when evaluated without retrieval, the original model performance is exactly maintained"; retrofitted models "achieve performance close to that of Retro models trained from scratch." — [RETRO](https://arxiv.org/abs/2112.04426)
- No explicit "frees capacity" claim; the stated aim is "to decouple these, by exploring efficient means of augmenting language models with a massive-scale memory without significantly increasing computations," and the conclusion that semi-parametric approaches "can provide an orthogonal, more efficient approach than raw parameter scaling." Downstream: NQ exact match RETRO 7.5B 45.5 vs closed-book baseline 7B 30.4 vs FiD 51.4; where retrieval fails, "the retrieved neighbours on these datasets are not helpful." — [RETRO](https://arxiv.org/abs/2112.04426)
- kNN-LM (Khandelwal et al., Nov 2019; 16-layer, 247M-parameter Transformer LM): WikiText-103 test perplexity 18.65 (base) to 16.12 (kNN-LM), 15.79 with continuous cache. — [kNN-LM, arXiv:1911.00172](https://arxiv.org/abs/1911.00172)
- Data-vs-memory experiment (Table 3): model trained on WIKI-100M 19.59; same model with a WIKI-3B datastore 13.73; model trained on WIKI-3B 15.17; "retrieving nearest neighbors from the corpus outperforms training on it." — [kNN-LM](https://arxiv.org/abs/1911.00172)
- Mechanism claims: "This approach allows rare patterns to be memorized explicitly, rather than implicitly in model parameters"; "learning similarity functions between contexts may be an easier problem than predicting the next word." Memorization control: training without dropout reaches zero training loss but validation perplexity 28.59 vs 17.96 for the normal model, and interpolating the memorizing LM with the original "improves validation perplexity by just 0.1" while kNN-LM gains 1.9. — [kNN-LM](https://arxiv.org/abs/1911.00172)
- Capacity yardstick (not retrieval, but the only quantitative statement of parametric knowledge capacity): "language models can and only can store 2 bits of knowledge per parameter, even when quantized to int8"; "a 7B model can store 14B bits of knowledge." — [Allen-Zhu and Li, arXiv:2404.05405](https://arxiv.org/abs/2404.05405)

### Inferences
- The retrieval results establish that an external store can substitute for parameters on perplexity, but they measure the system with the store attached. They do not show that the parameters inside a retrieval model were redeployed to other skills; RETRO-fit in fact guarantees the opposite (base weights untouched). The analogue of the user's question, "is a RETRO model better at non-retrievable skills than a baseline of the same size?", is not answered by these papers.
- kNN-LM's 100M-vs-3B experiment is the cleanest template for the user: hold the model fixed, vary what is offloaded, and ask how much training data the no-tool model needs to catch up. Translated: how many extra arithmetic examples (or steps) does the no-calls model need to match the calls model, and does that gap show up in story perplexity at all.
- The fact that RETRO gains are largest on corpora with near-duplicates (Wikitext103, C4) and smallest on Curation Corpus suggests offloaded memorization helps most when the offloaded content is lookup-like. Small-integer arithmetic under 256 is lookup-like, so if any freed-capacity effect exists it should be easiest to see there, but the per-parameter stakes are tiny (see Section 7).

### Gaps
- RETRO's per-subset Pile bits-per-byte and LAMBADA numbers are in figures only and were not extracted; the "25x" headline is from the abstract.
- I did not extract whether RETRO-from-scratch evaluated without retrieval matches the baseline (a "retrieval off" number would be the direct analogue of Toolformer-disabled).

## 6. Negative effects of tool-use training on general capabilities (forgetting, alignment-tax-style measurements)

### Takeaway
Since 2024 several papers document severe general-capability loss after tool/function-calling fine-tuning of 1.6B to 8B instruction-tuned models (e.g., Llama-3-8B-Instruct GSM8K 79.45 to 26.38 and HumanEval 59.15 to 0.00 after full fine-tuning on API-Bank; Gemma-2B MMLU 0.417 to 0.299), mitigated by mixing general text, adapters, or rehearsal. This is narrow-fine-tuning forgetting, not evidence about offloading itself, and it is absent from the pre-2024 calculator papers.

### Cited Findings
- CITI (Hao et al., Sep 2024; AAAI 2025; Llama-3-8B-Instruct, Phi-3-mini, Mistral-7B-Instruct-v0.2, tool data API-Bank and ToolAlpaca): "excessive fine-tuning on tool learning datasets severely diminishes the model's broader cognitive competencies." Table 3 (GSM8K / HumanEval / TriviaQA / MT-Bench): Llama-3 base 79.45 / 59.15 / 64.82 / 80.13; full FT 26.38 / 0.00 / 50.07 / 33.88; LoRA 76.88 / 53.05 / 64.84 / 68.00; CITI 77.33 / 54.88 / 64.69 / 76.94. Mistral base 44.81 / 35.37 / 59.21 / 75.66; full FT 2.05 / 0.00 / 13.50 / 10.63. Phi-3 base 82.71 / 60.37 / 53.08 / 81.28; full FT 73.09 / 51.83 / 53.32 / 66.81. CITI mixes 5,000 samples each from CodeAlpaca, MetaMathQA, TriviaQA and GPT-4-LLM into training; finding: "optimizing important components results in a significant decrease in general performance," but "the model may not fully learn the knowledge of calling tools only by optimizing unimportant components." — [CITI, arXiv:2409.13202](https://arxiv.org/abs/2409.13202)
- STE / "LLMs in the Imaginarium" (Wang et al., Mar 2024; ACL 2024; ~77K tool-use examples over 50 APIs; continual-learning study on Llama-Flan): "the model could drastically forget previously learned tools without rehearsal, with more distant ones being more severely forgotten"; with 10% replay plus 2,000 Flan-V2 examples per round, MMLU / BBH stayed at 38.5 to 40.2 / 36.8 to 39.1 versus base 37.2 / 39.5 and one-shot FT 38.7 / 40.8; "General language abilities are also retained as measured on MMLU and BBH." No no-rehearsal MMLU/BBH numbers are reported. — [STE, arXiv:2403.04746](https://arxiv.org/abs/2403.04746)
- Alopex (Nov 2024; full fine-tuning of 1.6B to 2B models for function calling): "We have also observed the phenomenon of catastrophic forgetting after fine-tuning the function call task"; intro states "a 16% drop in accuracy is observed" on MMLU. Gemma-2B base MMLU 0.4174 / GSM8K 0.1812 / ARC 0.4923 / HellaSwag 0.7154 vs after FT 0.2985 / 0.0129 / 0.4352 / 0.6314. Fox-1-1.6B base MMLU 0.4303 / GSM8K 0.3654 vs after FT 0.4196 / 0.2858. Mixing the function-call data 1:1 with the tiny-textbooks corpus: Gemma MMLU 0.2985 to 0.3600, GSM8K 0.0129 to 0.1236; Qwen1.5-1.8B MMLU 0.3685 to 0.4685, GSM8K 0.0349 to 0.3275; for Fox the mix is inconsistent (one variant's average fell from 0.8119 to 0.806). Table averages contain inconsistencies, so treat the average column with caution. — [Alopex, arXiv:2411.05209](https://arxiv.org/abs/2411.05209)
- Entropy-Adaptive Fine-Tuning (Jan 2026): standard SFT on agentic tool-use data raised Qwen3-4B-Instruct's BFCL score but lowered its general-capability average from 81.1 to 74.8 (from a search snippet; not verified against the paper). — [EAFT, arXiv:2601.02151](https://arxiv.org/abs/2601.02151)
- QLoRA tool-knowledge study on small models (May 2026): Gemma fell from 84.0% to 67.0% on a multiple-choice mix at rank 32, Qwen3 from 75.0% to 46.0%; quantization ruled out as cause (search snippet; not verified). — [arXiv:2605.17774](https://arxiv.org/abs/2605.17774)
- Over-reliance rather than forgetting: SMART (Qian et al., Feb 2025; ACL Findings 2025) defines "Tool Overuse" as relying on tools for tasks the model could do internally; its trained SMARTAgent "reduces tool use by 24% while improving performance by over 37%" and keeps accuracy with one-fifth the tool calls on GSM8K and MINTQA (abstract-level; numbers not verified in the body). — [SMART, arXiv:2502.11435](https://arxiv.org/abs/2502.11435)
- The classic mitigation is the one the user already uses by construction (mixed data stream): GenBERT lost 3 SQuAD EM when the MLM loss was dropped during numeric pre-training; Mialon et al. recommend mixing pre-training data to avoid the LM deviating "far from the original distribution." — [GenBERT](https://arxiv.org/abs/2004.04487); [Mialon et al.](https://arxiv.org/abs/2302.07842)

### Inferences
- All of this forgetting is post-hoc fine-tuning of an already-trained model on a narrow distribution; the GSM8K collapses in CITI and Alopex happen even though function-calling data contains no arithmetic, so they say nothing about "the model stopped doing arithmetic because a tool does it." They are irrelevant to a model trained from scratch on a mixed story+arithmetic stream, except as a reminder to keep the mixture and to test general ability, not just the tool task.
- The 2021 to 2023 calculator papers (Cobbe, TALM, Calc-X, ToolkenGPT, PAL) never reported this because they either froze the LM, prompted only, or did not evaluate general ability; the absence is a measurement gap, not a finding of no harm.
- No study tests the specific "use it or lose it" claim (internal arithmetic degrading because a calculator is available during training); the only data points (Toolformer disabled, SyReLM LMFT) go the other way.

### Gaps
- EAFT, the QLoRA study and SMART numbers were taken from search snippets or abstracts and not checked against full text.
- No paper measures general-ability change from calculator training specifically (as opposed to API/function-calling data).

## 7. What transfers to a 1.4M-parameter TinyStories + arithmetic model, and what would count as evidence

### Takeaway
No published result is within two orders of magnitude of the user's model; the literature says tool training "does not hurt" text perplexity at 6.7B (Toolformer, 0.1 resolution), that explicit supervised calling works down to 220M (TALM) and 110M-size encoders (GenBERT-style numeric injection), and that a learned decision of when to call is hard below ~775M (Toolformer). The user's 15.66 vs 15.33 (0.1 at equal story words) is consistent with "no cost" and is not evidence of freed capacity in either direction without seeds.

### Cited Findings
- Only matched-data perplexity precedent: Toolformer (disabled) 10.3 / 10.5 vs GPT-J + CC 10.3 / 10.5, one run, no error bars. — [Toolformer](https://arxiv.org/abs/2302.04761)
- Tool-call ability threshold in the self-supervised setting: "only emerges at around 775M parameters." — [Toolformer](https://arxiv.org/abs/2302.04761)
- Supervised calling at 220M (TALM) and 700M (Calcformer) with 150 to ~2k seed examples (TALM) or full datasets (Calc-X). — [TALM](https://arxiv.org/abs/2205.12255); [Calc-X](https://arxiv.org/abs/2305.15017)
- Smallest model in the arithmetic-learning literature: NanoGPT 10.6M, which learns 3-digit addition to 100% with 1,000 to 2,000 scratchpad examples but plateaus near 85% on plain format with 10,000; text mixing raises Shakespeare training perplexity somewhat (figure only). — [Lee et al.](https://arxiv.org/abs/2307.03381)
- Parametric capacity yardstick: about 2 bits of knowledge per parameter. — [Allen-Zhu and Li](https://arxiv.org/abs/2404.05405)
- Template for a data-efficiency test: kNN-LM, model trained on 100M tokens + datastore (13.73) vs model trained on 3B tokens (15.17). — [kNN-LM](https://arxiv.org/abs/1911.00172)

### Inferences
- Rough capacity budget (my arithmetic, not from any paper): with results under 256, there are about 33k valid addition pairs, about 33k subtraction pairs, and under 2k multiplication pairs, i.e. roughly 67k facts of 8 bits each, about 0.5M bits if memorized as a table. At 2 bits/parameter that is about 270k parameters, under 20% of a 1.4M model, and far less if the model learns carry rules instead of a table. So the maximum plausible "freed" capacity is a modest fraction of the network, and the tool model spends some of it learning the call syntax and when to fire. A perplexity difference from this would be small; the 0.1 to 0.3 differences the user sees are the right order of magnitude for either sign, which is why seeds and a size sweep matter.
- Loss masking makes the user's design stronger than Cobbe/Calc-X (which keep answer digits in the loss) and matches Toolformer's spirit; but the masked tokens also mean fewer loss-bearing tokens per step, which is why the equal-steps gap (0.33) exceeds the equal-story-words gap (0.1). Equal story words (or equal loss-bearing tokens) is the fair axis; Toolformer did not control for this either.
- Measurements with literature precedent that would speak to the hypothesis: (1) Toolformer-style tool-off evaluation of the calls model on arithmetic, to check internal skill did not vanish and to quantify how much arithmetic it still learned despite masking; (2) kNN-LM-style data matching: how many extra arithmetic examples or steps the no-calls model needs to reach the calls model's arithmetic accuracy, and whether story perplexity moves at all; (3) RETRO-style size sweep (e.g., 0.35M, 0.7M, 1.4M, 2.8M) each way, to see whether the calls curve is shifted toward fewer parameters on story perplexity, which is the only form in which "freed capacity" has ever been shown for retrieval; (4) GenBERT/CITI-style general-ability probes beyond perplexity (held-out story completion accuracy, grammar probes), since perplexity at equal data was flat in every precedent; (5) multiple seeds, because every precedent reports differences of 0.1 to 0.4 perplexity with no error bars.
- Because every precedent that controlled for data found "no cost" rather than "gain," the prior from the literature is that story perplexity will be equal within noise, and that any freed-capacity signal, if real, will be easier to see in arithmetic data efficiency or in a parameter sweep than in perplexity.

### Gaps
- Nothing published on tool-calling models under ~100M parameters with a matched control; the literature is silent, which is itself the answer: the user's experiment has no direct precedent, and the closest prior results (Toolformer Table 8) show equality, not improvement.
