# Train the call, mask the answer

Every in-text tool-use system that works, from GSM8K's 2021 calculator annotations to the 2025 reinforcement-learning systems, runs one loop: the model writes a call up to a fixed delimiter, decoding halts the moment that delimiter is sampled, the environment appends the result plus a closing marker, and decoding resumes with the result sitting in the context. The training consensus has moved from GSM8K's "they are all just tokens" to **keeping the tool's output in the model's input but out of the loss**, and the one ablation that measures this (Search-R1) puts the masking gain at nearly nine exact-match points. For the planned 4-layer, d_model-128, 64-token model the published evidence says the mechanics are learnable: a copy circuit needs only two attention layers, a from-scratch LLaMA of exactly this depth and width learned to parse operands into a calculator at **99.2%**, and 10M-parameter models learn arithmetic embedded in story text from a few thousand examples. The two real dangers are misdirected capacity and mislearned triggers: a d_model-128 model can learn the 0-255 addition table itself if the CPU's answer carries loss, which removes its incentive to call at all, and every surveyed system learned the call decision as a surface pattern that over-fires on number-bearing text unless no-call cases are scored. Two-call chaining is documented at 700M-33B scale (Calc-X averages 1.6 calls per chain; ToolkenGPT transfers one-hop training to multi-hop) and always depends on the model re-reading its own earlier result, so it must be trained explicitly, not expected to emerge. The recommendations that close this report are: a GSM8K-shaped call (`<calc> 12 + 5 =`) answered by one CPU token and a close marker; label −100 on the CPU-written span only; `use_calculator`-style validation with an operand log; a logit bias or top-k trigger on `<calc>` only if the model under-calls, with a hard cap of two calls per window; dense no-call negatives plus an irrelevance metric; explicit two-call traces evaluated on held-out templates across at least three seeds; and the expectation of high-90s in-distribution copy accuracy with a seed-dependent error tail and weak transfer to sentence shapes whose cue words differ from training.

## Every in-text tool loop stops at a delimiter, pastes the result, and resumes

Toolformer linearizes a call with its result as `<API> a_c(i_c) → r </API>`, and its first footnote says that in practice the token sequences `[`, `]` and `->` stand in for the three special tokens so that no vocabulary change is needed ([Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)). The loop is stated in one sentence: the model decodes normally "until M produces the "→" token", decoding is interrupted, the API is called, and decoding continues "after inserting both the response and the </API> token" ([Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)). A calculator example from its Table 10 reads `<API> Calculator(735 / 499) → 1.47 </API> 1.47 (735 / 499) times hotter than it should be`, and the calculator supports only the four basic operations with results rounded to two decimals ([Toolformer §3, Table 10](https://ar5iv.labs.arxiv.org/html/2302.04761)).

GSM8K uses the terser `<<expression=result>>` form, as in "The booth made $50 x 3 = $<<50*3=150>>150 selling cotton candy each day", and its stop signal is the ordinary `=` token ([grade-school-math README](https://github.com/openai/grade-school-math)). The sampling code generates one token at a time, checks whether the last token is in `EQUALS_TOKENS = set([28, 796, 47505])`, three GPT-2 ids that contain "=", and if `use_calculator(text)` returns a value it appends `str(answer) + ">>"` and keeps decoding ([calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py)). `use_calculator` is a whitelist validator: it returns `None` (no override) unless the text after the last `<<` contains `=`, has no `>>` yet, and has a left-hand side made only of characters in `"0123456789*+-/.()"`; the expression is then evaluated under a 3-second timeout, and "Evaluations that time out or throw an error result in the annotations being skipped and the model being sampled from as usual" ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168); [calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py)). The paper calls this a calculator that "will override sampling when the model chooses to use these annotations" ([GSM8K §4](https://ar5iv.labs.arxiv.org/html/2110.14168)); because the check fires immediately after `=`, no result token has been sampled yet, so the override is really a pre-emption (inference).

ToolkenGPT makes the call itself a vocabulary entry. Toolken embeddings W_τ are concatenated to the LM head so the next token is drawn from `softmax([W_ν ; W_τ] · h_{i−1})` over words and tools together, and sampling any toolken (ids 32000 and above for LLaMA) ends "reasoning mode" ([ToolkenGPT §3.1](https://ar5iv.labs.arxiv.org/html/2305.11554); [llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py)). The model then switches to a "tool mode" prompt of in-context demonstrations that writes the arguments in `[tool](arguments)` syntax, the call is executed, and "the returned value is sent back to the text in the reasoning mode" ([ToolkenGPT §3.1](https://ar5iv.labs.arxiv.org/html/2305.11554)). The code shows what "sent back" means: `cur_generation = cur_generation.split(op)[0] + str(res)` replaces the call text with the bare result, the call is kept in a side list and re-inserted only when later tool-mode prompts are built, and the next reasoning step disables digit tokens for one position so the model cannot extend the number ([inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py)). Its arithmetic demonstrations put the call right after the equals sign, `147+354=<add>(147,354)=501` ([ToolkenGPT appendix](https://arxiv.org/html/2305.11554)).

Calc-X (the "Calcformers") uses XML-style tags with small T5 models: `<gadget id="calculator">27/3</gadget><output>9</output>`, with the final answer in `<result>`; "By generating the closing </gadget> tag, model calls an external tool" and "The following tokens are inserted into the model's context by the tool", under greedy decoding through a patched `generate()` ([Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017); [calc-x README](https://github.com/prompteus/calc-x)). Chat-template function calling instead makes the call a whole assistant turn, `<tool_call>{json}</tool_call>` plus the end-of-turn token, and returns the result as a separate `tool`-role message that the template renders before a fresh assistant header ([HF chat templating](https://huggingface.co/docs/transformers/v4.44.0/en/chat_templating)); the docs warn that "Formatting such as whitespace and special tokens are model-specific. Make sure everything exactly matches the format a model was trained with" ([HF chat_templating_writing](https://huggingface.co/docs/transformers/main/en/chat_templating_writing)).

The RL-era tool-integrated reasoning systems are inline interleavers of the Calc-X kind with heavier payloads. ToRA's trajectory is r1 a1 o1 … r_n (rationale, program, output); execution triggers on the stop words "```output", the output is appended, and generation resumes until the answer appears in `\boxed{}` ([ToRA](https://arxiv.org/abs/2309.17452)). ReTool pauses when `</code>` is detected, sends the code to a sandbox, fills the output into `<interpreter></interpreter>`, and "continues generating the rollout until either providing a final answer o or producing a new code snippet", reusing the KV cache from before the call ([ReTool §2.3](https://arxiv.org/abs/2504.11536)). ToRL returns only the last line of a traceback and caps calls at C = 1 per response by default ([ToRL](https://arxiv.org/abs/2503.23383)); ARTIST uses `<think>`, `<python>`, `<output>` and `<answer>` segments ([ARTIST](https://arxiv.org/abs/2505.01441)); Search-R1 uses `<search>` and `<information>` with a budget of B = 4 actions ([Search-R1](https://arxiv.org/abs/2503.09516)). PAL and PoT are the exception that defines the alternative: they emit one program per answer, chain through named variables, run the interpreter once, and so never ask the model to copy a number ([PAL](https://arxiv.org/abs/2211.10435); [PoT](https://arxiv.org/abs/2211.12588)).

| System | Model writes | Stop signal | Environment writes | Call text stays in context |
|---|---|---|---|---|
| Toolformer | `[Calculator(735 / 499) ->` | `->` | `1.47]` | yes |
| GSM8K | `<<50*3=` | `=` inside an open `<<` | `150>>` | yes |
| ToolkenGPT | toolken, then `(147,354)` in tool mode | the toolken itself; `)` ends arguments | bare result replaces the call text | no (kept in a side list) |
| Calc-X | `<gadget id="calculator">27/3</gadget>` | `</gadget>` | `<output>9</output>` | yes |
| ToRA / ToRL / ReTool | python code fence or `<code>…</code>` | "```output" or `</code>` | output block or `<interpreter>…</interpreter>` | yes |
| Chat template | `<tool_call>{json}</tool_call>` + end of turn | end-of-turn token | a `tool`-role message, then a new assistant header | yes, as prior turns |

With every integer 0-255 a single token, the GSM8K shape costs about six tokens per call (open, operand, operator, operand, `=`, result, close), while the Toolformer shape costs roughly double because it carries a tool name, parentheses, an arrow and a bracket (inference). ToolkenGPT's "strip the call, keep the number" leaves only one token behind, the most context-frugal option, but it means the model never conditions on its own call text while continuing (inference).

## Modern systems keep the result in the input but out of the loss

The older calculator systems trained on everything. GSM8K is explicit: "During training, there is no special distinction between the annotated tokens and the rest of the solution: they are all just tokens", with the calculator applied only at test time ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)). Toolformer fine-tunes on its augmented corpus "using a standard language modeling objective", where the inserted calls are `e(c, r)` and therefore include the response, and no sentence about masking the response appears in the paper ([Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)). Calc-X reports "cross-entropy loss on all tokens" ([Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017)). The two scratchpad papers likewise put every intermediate step in the loss ([Nye et al.](https://arxiv.org/abs/2112.00114); [Lee et al.](https://arxiv.org/abs/2307.03381)).

ToolkenGPT is the first calculator paper to mask. Its parallel target sequence replaces the result tokens with `[N/A]`, "indicating neglect in loss calculation", and its objective sums −log P(t′_i | t_<i) only over positions where t′_i ≠ [N/A]: "[N/A] is introduced to skip the generation of the returned value of a tool call" ([ToolkenGPT §3.2](https://ar5iv.labs.arxiv.org/html/2305.11554)). The code does exactly `labels[s] = func_id + 32000; labels[s+1:t] = -100` and `F.cross_entropy(..., ignore_index=-100)`, with the whole LLM frozen and only the `func_embed` matrix trained ([llama/model.py](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py); [train_llama.py](https://github.com/Ber666/ToolkenGPT/blob/main/train_llama.py)). The important subtlety is that masking removes the result as a *target*, never as an *input*: later positions still attend to the result and still carry loss, so the model is trained to use the number without being trained to produce it (inference from the code).

The chat-template ecosystem standardized the same choice. Hugging Face's `return_assistant_tokens_mask` marks assistant tokens 1 and user or system tokens 0 through `{% generation %}` blocks ([HF tokenization_utils](https://huggingface.co/docs/transformers/main/en/internal/tokenization_utils)); TRL's `assistant_only_loss=True` scores only assistant responses using the −100 ignore index ([TRL SFT Trainer](https://huggingface.co/docs/trl/main/en/sft_trainer)); and TRL's bundled templates state the boundary precisely: "Wrap the parts of a model turn that the model emits (thinking channel, tool calls, content, and the closing `<turn|>`) ... Tool responses embedded in the turn come from the environment and stay outside the generation block" ([TRL chat templates](https://huggingface.co/docs/trl/main/en/chat_templates)). SmolLM3's shipped template renders `tool`-role messages as user turns outside the generation block ([SmolLM3-3B template](https://huggingface.co/HuggingFaceTB/SmolLM3-3B/raw/main/chat_template.jinja)). The stated reason: "The gradient flows only through tokens the model itself would be expected to generate", because "You don't want the model's gradients to memorize tool outputs as if it had to generate them itself", while the results stay in the sequence because "the model needs to condition on them to write the final answer" ([Gustafson](https://thegustafson.com/blog/tool-use-finetuning); [Raschka](https://sebastianraschka.com/faq/docs/when-mask-prompt-tokens.html)).

Every RL system masks, and one measures the effect. ReTool masks `<interpreter>` feedback "ensuring training stability" ([ReTool §2.3.2](https://arxiv.org/abs/2504.11536)); ARTIST explains that "Applying token-level loss uniformly can cause the model to imitate deterministic tool outputs, rather than learning effective tool invocation strategies" ([ARTIST §2.2](https://arxiv.org/abs/2505.01441)); ToRL masks the sandbox OBSERVATION ([ToRL](https://arxiv.org/abs/2503.23383)); Self-RAG masks retrieved chunks ([Self-RAG](https://arxiv.org/abs/2310.11511)). Search-R1's ablation gives the number: **average EM across seven datasets of 0.431 with retrieved-token masking versus 0.343 without** for Qwen2.5-7B, and 0.303 versus 0.262 for the 3B model ([Search-R1 Table 6](https://arxiv.org/abs/2503.09516)).

The masking question bites harder at d_model 128 than anywhere in this literature, and the reason is capacity, not its absence (inference, built on the following evidence). A one-layer transformer with d = 128, four heads of dimension 32 and a 512-unit MLP learns the full 113 × 113 modular-addition table from 30% of the pairs, forming a generalizing Fourier circuit after roughly 10,000 full-batch epochs with weight decay 1 ([Nanda et al.](https://arxiv.org/abs/2301.05217)). A 10.6M-parameter NanoGPT learns 3-digit addition to 100% from about 1,000 detailed-scratchpad or 2,000 simplified-scratchpad examples, and with reversed output shows a phase transition around 2,500 ([Lee et al.](https://arxiv.org/abs/2307.03381)). The target's addition over single-token numbers is a 256 × 256 lookup, simpler than either task. If the CPU's `17` is a training target, every call snippet becomes a labelled (a, b) → sum example and gradient pushes the model to predict the sum from the operands in context; large LLMs given single-token numbers 0-1000 do this with "a 'bag of heuristics'" (operand-range and modular-pattern neurons, about 1.5% of neurons per layer) rather than a clean algorithm, and the heuristics are the mechanism from early checkpoints on ([Nikankin et al.](https://arxiv.org/abs/2410.21272)). A model that half-adds has no reason to pay six tokens for `<calc>` and will produce confident wrong sums that disagree with the CPU (inference). Magister et al. show the post-hoc alternative for comparison: T5 models write `a op b = c` themselves and a calculator rewrites `c` afterwards, carrying the fix forward into later equations, and under that scheme even the 60M-parameter T5-small "outperforms the baseline T5 XXL" at 8.11% on GSM8K ([Magister et al.](https://ar5iv.labs.arxiv.org/html/2212.08410); [t5-small](https://huggingface.co/google-t5/t5-small)).

## The call decision comes from data density, a loss filter, or a reward, and over-calling is the default failure

Three mechanisms teach a model *when* to call. The first is annotation density. GSM8K's annotations "were generated by a combination of hard-coded logic and a finetuned language model" that "is highly unlikely to generate any incorrect annotations, but it is not uncommon for it to ignore some lines that could be annotated" ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)). Calc-X injects calls wherever a regex finds "expression = number" and sympy agrees, giving **1.6 calculator calls per reasoning chain**, and its one failure is instructive: on AQuA-RAT the calculator was used inconsistently at test time "due to the low average number of tool calls inside the AQuA-RAT training split", so the learned call rate tracked the training call density ([Calc-X §4-5](https://ar5iv.labs.arxiv.org/html/2305.15017)). SMART-ER labels each sub-step A(s_i) = 1 (tool) or 0 (parametric), with a justification for each, and SFT on that data cut Llama-3.1-8B's calls on GSM8K from 2.53 to 0.76 per problem while accuracy held (83.17 to 83.40); the same model's untreated overuse rate O = α·β (the fraction of tool-free-solvable questions on which it still calls) exceeded 50% ([SMART](https://arxiv.org/abs/2502.11435)). Self-RAG gives the decision an explicit token, Retrieve ∈ {yes, no, continue}, and retrieves when its normalized probability exceeds a threshold (0.2 by default) ([Self-RAG](https://arxiv.org/abs/2310.11511)).

The second mechanism is Toolformer's loss filter. Candidate positions are those where p_M(`<API>` | prefix) > τ_s, up to m calls are sampled per position, and a call is kept only if L⁻_i − L⁺_i ≥ τ_f, where L⁺ is the weighted cross-entropy of the following tokens given call-plus-result as prefix and L⁻ is the better of no call and call-without-result; weights w̃_t = max(0, 1 − 0.2·t) mean only the five tokens after the call count ([Toolformer §2, Appendix A](https://ar5iv.labs.arxiv.org/html/2302.04761)). The calculator needed looser thresholds than other tools (τ_s = 0, k = 20, m = 10, τ_f = 0.5, versus defaults 0.05, 5, 5, 1.0) and a pre-filter requiring "at least three numbers within a window of 100 tokens", and still yielded only **3,680 calculator examples at τ_f = 0.5 (994 at 1.0, 138 at 2.0) against 207,241 for Wikipedia search** ([Toolformer Table 2, Appendix A](https://ar5iv.labs.arxiv.org/html/2302.04761v1)). At decode time the model starts a call "whenever it is one of the k most likely tokens" with k = 10, "to increase the disposition of our model to make use of the APIs", and makes "at most one API call per input to make sure the model does not get stuck in a loop" ([Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)). The k dial moves call rates from 40.3% (k = 1) to 98.1% (k = 10) on LAMA T-REx and from 8.5% to 100% on WebQS, and on the math benchmarks "for 97.9% of all examples the model decides to ask the calculator tool for help" ([Toolformer §4.2, §5, Table 9](https://arxiv.org/abs/2302.04761)). The authors also admit the decision is brittle: models "often [are] sensitive to the exact wording of their input when deciding whether or not to call an API", and they argue "some amount of noise in the API calls that are not filtered can actually be useful as it forces the model finetuned on C* to not always blindly follow the results of each call" ([Toolformer §5, §7](https://ar5iv.labs.arxiv.org/html/2302.04761)). ToolkenGPT supervises the decision at the token level instead: the toolken is the target exactly where a result begins, and since the loss also covers every word position with the LLM frozen, the only way to lower loss at a word position is to push the toolken logits down, so Eq. (2) teaches "call here" and "don't call here" at once (inference from [ToolkenGPT §3.2](https://ar5iv.labs.arxiv.org/html/2305.11554)); at decode time it adds a scalar `logits_bias` of 3.0 for GSM8K-XL, 2.7 for FuncQA one-hop and 4.0 for multi-hop ([ToolkenGPT README](https://github.com/Ber666/ToolkenGPT)).

The third mechanism is reward. Outcome-only RL works for accuracy and reshapes calling aggressively: ReTool's reward is +1 if the boxed answer is equivalent else −1, chosen to "alleviate reward hacking", and with it Qwen2.5-32B-Instruct reaches **67.0% on AIME2024 after 400 steps versus 40.0% for text-only RL after more than 1,000 steps**; the code ratio rises to "nearly 98%" of responses, correct code executions on the test set go from 1k to 5k, response length falls 40% (10k to 6k tokens), and the first-code position "advances during the RL training process" ([ReTool Table 1, §3.3](https://arxiv.org/abs/2504.11536)). ToRL tested an extra −0.5 penalty for non-executable code and found "adding the penalty does not improve performance" ([ToRL](https://arxiv.org/abs/2503.23383)); Search-R1 skipped a format reward because its model "already demonstrates strong structural adherence" ([Search-R1](https://arxiv.org/abs/2503.09516)). Where format rewards are used, binary beats partial credit: Nemotron Tool-N1-7B scores 84.82 BFCL average with a binary reward that requires both `<think>`/`<tool_call>` tags and an exact call match, 83.74 with 0.2 partial credit for format, and 81.94 with the format constraint removed, and its pure-RL model (83.24) matches SFT-then-RL (83.17) ([Nemotron Tool-N1 Tables 3-4](https://arxiv.org/abs/2505.00024)). ToolRL's R_format ∈ {0, 1} plus R_correct ∈ [−3, 3] must keep correctness heavier: rescaling correctness to match format dropped Qwen2.5-1.5B from 46.20% to 39.47% overall and its irrelevance detection from 56.44% to 16.44%; a length reward was worse still (33.23% overall, irrelevance 4.52%); an abrupt two-stage reweighting hurt while a smooth linear one helped; and GRPO from the raw instruct model gave "~10% absolute gains over SFT trained on the same data volume" ([ToolRL Tables 5-6, §4.3-5.2](https://arxiv.org/abs/2504.13958)).

Outcome-only rewards also leave the call decision unsupervised, and five papers document the resulting over-calling and its fixes. "Spurious Tool Use" states the mechanism, "Spurious tool calls incur no penalty as long as the final answer remains correct", and shows it with counterfactual pairs: an injected "[WEB INDEX]" cue raised unnecessary search calls on GSM8K by **+39.2 points (40.1% with the cue versus 0.9% without)** after only 30 GRPO steps, shortcuts "form only for the well-learned tool", and a dense −0.5 penalty on judge-labelled unnecessary calls brought the cue effect to +0.3 or less without hurting accuracy ([Spurious Tool Use Tables 1-2, §4-5](https://arxiv.org/abs/2609.16268)). OTC multiplies the answer reward by a cosine of the call count so that "when the final answer is incorrect, r_φ is 0", cutting Search-R1-PPO's 3.282 calls per question to 1.040 (−68.3%) at unchanged EM (0.449 versus 0.446), and notes that "as language models scale up, they may tend to over-rely on external tool calls unless explicitly penalized" ([OTC §3-4, Table 1](https://arxiv.org/abs/2504.14870)). EAPO's shaping term exp(−β(c_i − c_min)), gated by the fraction of failed rollouts so hard questions keep the raw reward, with at least 2 of 16 rollouts generated tool-free, keeps HotpotQA calls at 1.99 versus 3.49 without shaping ([EAPO](https://arxiv.org/abs/2606.02132)). AdaTIR penalizes calls only on correct rollouts of easy questions and takes GSM8K from 0.83 to 0.02 calls per problem while accuracy rises 91.0 to 92.8, but reports a "sign reversal problem" when every rollout is correct and efficiency alone drives the advantage, fixed with clipped advantage shaping; its failure analysis attributes 9.2% of GSM8K failures and 57.7% of AIME failures to tool-induced noise ([AdaTIR](https://arxiv.org/abs/2601.14696)). ARTIST, with a composite reward, moves the opposite way on hard problems, from 0.3 to more than 3 calls per AIME query, while reducing calls on MATH-500 "when internal reasoning suffices" ([ARTIST §5.1.2](https://arxiv.org/abs/2505.01441)).

| Reward design | Base term | Call-cost term | Reported effect on calling |
|---|---|---|---|
| ReTool | ±1 on the answer | none | code in ~98% of responses; correct executions 1k → 5k |
| ToRL | ±1; tested −0.5 for non-executable code | none (penalty did not help) | calls capped at C = 1 |
| Nemotron Tool-N1 | binary: tags present and exact call match | none | binary beats partial credit by ~1-3 points |
| ToolRL | format {0,1} + correctness [−3,3] | none; length reward hurt | irrelevance detection 56% → 4.5% under a length reward |
| OTC | answer × cos/sin of call count | multiplicative, zero if wrong | 3.28 → 1.04 calls at equal EM |
| EAPO | answer × exp(−β(c − c_min)), difficulty-gated | multiplicative | 3.49 → 1.99 calls on HotpotQA |
| AdaTIR | answer − λ·sin(πN/2N_max), correct and easy only | additive | GSM8K 0.83 → 0.02 calls, accuracy +1.8 |
| Spurious Tool Use | answer − 0.5 per judged-unnecessary call | additive, per call | cue-driven calls +39.2 → +0.3 |

## Chaining works where the model re-reads its own result, and nobody measures the copy error directly

Two families represent multi-step tool use. In the program family (PAL, PoT) chaining happens inside the program through variables, so a number is never re-typed; PAL's ablation shows how much that naming carries, since replacing meaningful variable names with random characters "further decreases accuracy, and performs worse than CoT", and on GSM-HARD (one number per question replaced by a random integer of up to seven digits) CoT falls from 65.6% to 23.1% while PAL falls only from 72.0% to 61.2% ([PAL §4.1, §6](https://arxiv.org/abs/2211.10435)). In the inline family the model must re-read each result and write the next call. Calc-X's training target shows the burden exactly: "you have 32-3-2= <gadget id="calculator">32-3-2</gadget> <output>27</output> $27. You spend 27/3= <gadget id="calculator">27/3</gadget> <output>9</output> 9 dollars on the turkey. You have 27-9= <gadget id="calculator">27-9</gadget> <output>18</output> $18 left", where the 27 produced by the first call is re-typed by the model as an operand of the second and third ([Calc-X Fig. 1-2](https://ar5iv.labs.arxiv.org/html/2305.15017)). This is the only family that fits a 64-token window (inference).

How often chaining actually happens is modest. ToRA averages **1.02 tool rounds per problem** at inference with a training maximum of three ([ToRA §3.4](https://arxiv.org/abs/2309.17452)); ToRL's default is one call, and allowing two adds about 2% accuracy at the cost of step time rising from 237 s to 288 s ([ToRL](https://arxiv.org/abs/2503.23383)); among ReAct's correct trajectories, those using seven steps on HotpotQA make up only 0.84% ([ReAct footnote 3](https://arxiv.org/abs/2210.03629)). The systems closest to the target's scale chain the most: Calc-X's 1.6 calls per chain at 700M-3B, and ToolkenGPT's toolkens, trained "solely using one-hop synthetic data" (611 samples), reaching **0.15 on FuncQA multi-hop versus 0.06 for ReAct and 0.03 for CoT** with a LLaMA-33B backbone, "a degree of generalization of toolken embeddings" ([ToolkenGPT Table 2, §4.1](https://arxiv.org/abs/2305.11554)). Toolformer is the cautionary case: it cannot chain at all, and the authors explain why, "API calls for each tool are generated independently; as a consequence, there are no examples of chained tool use in the finetuning dataset" ([Toolformer §7](https://ar5iv.labs.arxiv.org/html/2302.04761)). The lesson is direct: chaining appears when chained traces are in the training data and not otherwise (inference).

No paper reports the error that matters most for the target, copying the previous result wrongly into the next call. The nearest proxies are PoT's error analysis, in which **47% of failures are "value grounding" errors** where "the model fails to assign correct values to the variables relevant to the question", versus 33% logic errors ([PoT §3.4](https://arxiv.org/abs/2211.12588)), and ToRA's human-labelled failure modes on MATH: 38% reasoning, 5% "Hallucination: Fabrication of numbers or answers", 9% syntax, 9% runtime ([ToRA Table 4](https://arxiv.org/abs/2309.17452)). ReAct adds a failure pattern specific to interleaved traces, "the model repetitively generates the previous thoughts and actions" ([ReAct §3.3](https://arxiv.org/abs/2210.03629)). Magister's carry-forward calculator exists precisely because a wrong intermediate propagates: it "replaces the right-hand side with the calculated output, to avoid arithmetic mistakes being carried forward" and also patches later re-uses of the wrong number ([Magister et al. §4](https://ar5iv.labs.arxiv.org/html/2212.08410)). With single-token numbers the digit-level copy error disappears but the which-number-to-copy error does not, so a two-step evaluation should log whether the second call's operand equals the first call's result (inference). ToRA's output-space shaping is the one documented trick for improving multi-step traces cheaply: sample 64 trajectories per question, keep correct ones, repair wrong ones by keeping a prefix and letting a teacher complete it greedily, and the gains (+3.4 GSM8K, +4.0 MATH on average) come "with greater benefits for smaller models" ([ToRA §2.3, §3.5.2](https://arxiv.org/abs/2309.17452)).

## A 4-layer, d_model-128 model can copy and parse, but it will try to add if you let it

The copy the target needs, attend from "has" back to the token after the most recent `=` and reproduce it, is an induction-style circuit, and such circuits need two attention layers composed through keys (inference on the mechanism). Elhage et al. show that one-layer attention-only models are "an ensemble of bigram and 'skip-trigram' models" whose copying heads move tokens "only to places where bigram-ish statistics make them seem plausible", with factored "skip-trigram bugs", whereas two-layer models form induction heads by K-composition between a previous-token head and second-layer heads, and these "only develop in models with at least two attention layers" ([Elhage et al.](https://transformer-circuits.pub/2021/framework/index.html)). An induction head "can operate on repeated sequences of completely random tokens", which is what makes it robust to distribution shift ([Elhage et al.](https://transformer-circuits.pub/2021/framework/index.html)). Olsson et al. find these heads forming "abruptly in a narrow window early in training (roughly 2.5 to 5 billion tokens)", the only non-convex bump in the loss curve, and that "almost all the in-context learning in small attention-only models appears to come from these induction heads" ([Olsson et al.](https://transformer-circuits.pub/2022/in-context-learning-and-induction-heads/index.html)). That window belongs to d_model-768, 8192-context, 65k-vocabulary models and does not transfer to a 5M-token run; with a 64-token context, story text supplies almost no induction pressure, so the inserted calc snippets must supply it directly as a supervised copy task (inference). Small from-scratch decoders do learn such tasks: "copy with unique tokens" length-generalizes to 96% exact match, and the authors note induction heads "are reliably learned even by simple Transformers", while "copy with repeat tokens" gets 0% ([Zhou et al. 2023](https://arxiv.org/abs/2310.16028)).

Two documented copy failure modes map onto the target. Transformers copy by hashed n-gram lookup and "start dropping when the inputs contains duplicate sequences of 5 or more tokens", behaving like a 5-gram retriever ([Jelassi et al.](https://arxiv.org/abs/2402.01032)); so if the same number appears twice ("12 apples ... 12 + 5 = 17"), copying can key on the wrong occurrence (inference). And reading the most recently written value from context is glitchy even when trivial: on flip-flop languages a 19M-parameter transformer shows "a long, irregular tail of errors" that "varies significantly between random seeds ... and even between iterates within the same training run", while a 133K-parameter one-layer LSTM "achieves 100% accuracy, on 100 out of 100 runs"; attention sharpening cuts errors "by an order of magnitude" but nothing short of out-of-distribution training data "could fully eliminate attention glitches" ([Liu et al.](https://arxiv.org/abs/2306.00946)). For the target this predicts a nonzero tail of wrong-number copies at 100% in-distribution training accuracy, worst when 12, 5 and 17 sit within a few tokens, and large seed variance (inference).

On capacity for the parsing half, one data point sits at exactly the target's width and depth. Saldyt and Kambhampati train "a scaled LLaMA with a dimension of 128, 4 transformer heads, 2 key-value heads, and 4 transformer layers" from scratch on 45,151 one-step problems such as "Add 3 and 4", with answer-only cross-entropy, and "By 62 epochs, the model can use the calculator with 99.2% accuracy on the test set, and by 132 epochs the accuracy is 100%"; their calculator is a differentiable lookup table receiving one-hot operands from the final layer, not a text-level call, and they warn that answer-only supervision gives "no guarantee that correct tool use behavior will be learned" ([Saldyt & Kambhampati](https://arxiv.org/abs/2407.04899)). TinyStories locates the target on the capability map: "the ability to generate a completion that is consistent with the beginning of the story emerges when the hidden size of the model increases from 64 to 128", one-layer models "struggle quite substantially with following instructions ... and 2 layers seem to be sufficient for a certain extent of instruction-following", and the 1M-parameter 8-layer model "fails to answer any factual prompt correctly" ([Eldan & Li](https://arxiv.org/abs/2305.07759)). The target, at hidden 128 and four layers, sits right at both thresholds, which is consistent with coherent-but-shallow stories and says nothing about arithmetic, since the TinyStories paper reports no number or arithmetic evaluation at all ([Eldan & Li](https://arxiv.org/abs/2305.07759)).

The mixed-corpus precedent is Lee et al.'s Shakespeare experiment: a character-level 10.6M model trained on 1.1M characters of text with 10,000 plain and 3,000 scratchpad addition examples inserted "between dialogue chunks" keeps addition accuracy "high ... even with the inclusion of a text prompt, given a substantial number of addition examples", but its behaviour is prompt-sensitive, with zero-shot addition at 84.06%, 96-97% after an arithmetic exemplar, and 88.71% after a text exemplar ([Lee et al.](https://arxiv.org/abs/2307.03381)). Scratchpads help most at small scale, cutting the data for 3-digit addition to ~1,000 examples versus a plateau "at slightly over 85% even with 10,000 samples" for plain format, and noisy intermediate values slow learning but "with enough samples, the model ultimately achieves full accuracy" ([Lee et al.](https://arxiv.org/abs/2307.03381)). Nye et al.'s pretrained models from 2M to 1B parameters solve long addition with a scratchpad only "beyond a critical model size", with the 2M model at the bottom of the curve, so they offer no positive evidence at 2M ([Nye et al.](https://arxiv.org/abs/2112.00114)). Toolformer's negative result, that "the ability to leverage the provided tools only emerges at around 775M parameters" among GPT-2 models, concerns self-supervised discovery of calls in open web text with 1,024-token contexts and does not predict failure for a fixed, densely supervised call format (inference from [Toolformer §4.4](https://ar5iv.labs.arxiv.org/html/2302.04761)).

Composition is where four layers are tightest. Wang et al. find that implicit two-hop composition in an 8-layer model generalizes in-distribution only after "around 50 times the steps taken to fit the training data" and "never" out of distribution, because "lower layers (0-5) retrieve the first-hop fact ... upper layers (5-8) retrieve the second hop" and OOD atomic facts "are simply not stored in the upper layers" ([Wang et al.](https://arxiv.org/abs/2405.15071)). Ye et al. find "The depth of the language model is crucial for its reasoning ability" on synthetic grade-school problems with step-by-step solutions ([Ye et al.](https://arxiv.org/abs/2407.20311)). The target's chain is explicit and verbalized, closer to Zhou et al.'s observation that a scratchpad "unroll[s] a loop, turning a next-token problem that requires n sequential steps" into local steps ([Zhou et al. 2023](https://arxiv.org/abs/2310.16028)) than to Wang's implicit composition, so each step is a short copy-plus-template operation, the regime small models handle best; but with four layers there is little room to separate "tag the result slot", "copy", and "write the template", so expect a surface trigger rather than general variable binding (inference).

## Design recommendations for the `<calc>` story GPT

### Call format: GSM8K's shape in the model's own tokens, with a unique close marker

Keep the planned `<calc> 12 + 5 =` and let the CPU write one result token followed by a close token (for instance `</calc>`), so a call is seven tokens and two calls fit in 14 of the 64 (inference on cost; shape from [GSM8K](https://github.com/openai/grade-school-math) and [Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017)). Three details are load-bearing. First, make `=` a single vocabulary id with no merges: GSM8K had to enumerate three GPT-2 ids containing "=" in `EQUALS_TOKENS`, and any merge missing from the trigger set means the calculator silently never fires ([calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py); inference on the consequence). Second, trigger only on `=` inside an open, unclosed `<calc>` span, exactly as `use_calculator` conditions on "after the last `<<`, no `>>` yet", so an `=` in prose can never fire the CPU ([calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py)). Third, keep the call text in the context rather than stripping it ToolkenGPT-style: Calc-X's chained traces show the model re-reading its own earlier call and output to write the next call, and at 14 tokens for two calls the context cost is affordable (inference from [Calc-X Fig. 2](https://ar5iv.labs.arxiv.org/html/2305.15017) and [inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py)). A dedicated close marker written by the CPU gives the copy circuit a unique key immediately adjacent to the result, which the induction-head mechanism needs and which reduces Jelassi-style collisions when the result value also appears earlier in the story (inference from [Elhage et al.](https://transformer-circuits.pub/2021/framework/index.html) and [Jelassi et al.](https://arxiv.org/abs/2402.01032)). An untested refinement is to number the marker per call (`<r1>`, `<r2>`) so the second copy does not depend on a "most recent write" read, which is exactly the flip-flop operation Liu et al. found glitchy (inference; no source tests this).

### What to mask: the CPU-written span only, and run the GSM8K variant as the ablation

Set the label to −100 on the token(s) the CPU writes, the result and, following the TRL convention that "Tool responses embedded in the turn come from the environment and stay outside the generation block", the close marker too ([TRL chat templates](https://huggingface.co/docs/trl/main/en/chat_templates); mechanics from [ToolkenGPT](https://github.com/Ber666/ToolkenGPT/blob/main/llama/model.py)). Keep ordinary next-token loss on everything the model writes: `<calc>`, both operands, the operator, `=`, and all following prose including the copied number in "now he has 17 apples", because the copy is never trained if its target is masked (inference). The masked result stays in the input, so later positions learn to read it, which is the whole point of the ToolkenGPT `[N/A]` design and of Search-R1's nine-point masking gain ([ToolkenGPT §3.2](https://ar5iv.labs.arxiv.org/html/2305.11554); [Search-R1 Table 6](https://arxiv.org/abs/2503.09516)). Then run GSM8K's "all just tokens" variant as a controlled ablation ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168)); the prediction, which no source tests at this scale, is that the unmasked model partially learns the 0-255 table (it has the capacity of Nanda's one-layer d-128 model many times over), begins writing sums that disagree with the CPU, and calls less often because calling no longer lowers its loss (inference from [Nanda et al.](https://arxiv.org/abs/2301.05217), [Lee et al.](https://arxiv.org/abs/2307.03381), [Nikankin et al.](https://arxiv.org/abs/2410.21272)). If internal arithmetic is wanted as a separate capability, train it in separate snippets, not through the tool's answer (inference).

### Decode-time trigger and validation: copy `use_calculator`, log operands, cap calls

Validate exactly as GSM8K does and refuse to fire on anything else: between `<calc>` and `=` require exactly NUMBER OPERATOR NUMBER with the operator in {+, −, ×}, operands guaranteed 0-255 by the vocabulary, and a defined behaviour for subtraction below zero and products or sums above 255 (either the data generator never produces them, or the CPU returns a fixed error token the model has seen in training) ([calculator.py](https://github.com/openai/grade-school-math/blob/master/grade_school_math/calculator.py); overflow handling is inference). On a malformed call, GSM8K's disposition, skip the override and keep sampling so the model writes its own result, is the simplest and is what T5-small-with-calculator effectively did; ToolkenGPT's alternative, backtrack to the next-most-likely token, is heavier ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168); [inference_modes.py](https://github.com/Ber666/ToolkenGPT/blob/main/inference_modes.py)). Log every call's operands and the CPU's output, because the literature never separates wrong-argument calls from misuse of a correct result, and in this setup all three cases (right call, wrong operands, right result miscopied) are directly observable (inference, gap noted across all sources). Use greedy decoding during calls, as Calc-X and Toolformer do ([Calc-X](https://ar5iv.labs.arxiv.org/html/2305.15017); [Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)). If the model under-calls after supervised training, the two documented dials are an additive bias on the `<calc>` logit (ToolkenGPT used 2.7-4.0 for arithmetic) and Toolformer's rule of opening a call whenever `<calc>` is in the top-k (k = 10) ([ToolkenGPT README](https://github.com/Ber666/ToolkenGPT); [Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)); both exist because fine-tuned models under-call, and both must be paired with a hard cap, two calls per 64-token window, since Toolformer limited itself to one call per input to avoid loops, ToRL to one or two, and Search-R1 to four ([Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761); [ToRL](https://arxiv.org/abs/2503.23383); [Search-R1](https://arxiv.org/abs/2503.09516)). Forbid `<calc>` inside an open call. For measurement, Toolformer's "disabled" condition, setting P(`<calc>`) to zero on the same weights, isolates the tool's contribution and gave +23 to +29 points on its math benchmarks ([Toolformer Table 4](https://ar5iv.labs.arxiv.org/html/2302.04761)).

### Teaching the call decision without over-calling: score the silences

Annotate every arithmetic step in the generated problems (GSM8K's policy) and deliberately include negatives that no calculator paper included: narrative sentences carrying numbers with no question, questions whose answer is a number stated in the text, and quantities in words; SMART-ER's A(s_i) = 0 steps are the supervised analogue and cut calls by two thirds at unchanged accuracy ([GSM8K Appendix C](https://ar5iv.labs.arxiv.org/html/2110.14168); [SMART](https://arxiv.org/abs/2502.11435)). Because the model is trained end to end with next-token loss on the whole story, every non-call position already acts as a "don't call here" example in the way ToolkenGPT's Eq. (2) does for a frozen LLM, provided such positions exist in quantity (inference from [ToolkenGPT §3.2](https://ar5iv.labs.arxiv.org/html/2305.11554)). Calibrate call density deliberately: Calc-X's AQuA-RAT result shows the learned call rate follows the training split's call density, and Toolformer's pre-filter (only number-dense text) produced a model that called on 97.9% of math inputs, which is indistinguishable from "always call" when only tool-needing problems are evaluated ([Calc-X §5](https://ar5iv.labs.arxiv.org/html/2305.15017); [Toolformer §4.2](https://ar5iv.labs.arxiv.org/html/2302.04761)). So report, per checkpoint, an irrelevance-detection accuracy on no-call cases (ToolRL's most volatile metric), the SMART overuse rate O = α·β from a tool-disabled pass, and Spurious-Tool-Use counterfactual pairs ΔTool(Y−N), where the obvious cue for this model is "two number tokens in one sentence" ([ToolRL Table 5](https://arxiv.org/abs/2504.13958); [SMART](https://arxiv.org/abs/2502.11435); [Spurious Tool Use §3](https://arxiv.org/abs/2609.16268); cue choice is inference). Toolformer's filter can also be reused in its model-agnostic half: insert a rule-generated call at a candidate position only if conditioning on call-plus-result lowers the tiny model's own loss on the following tokens by τ_f, which answers "is this call worth its tokens here?" with the model's own perplexity (inference from [Toolformer §2](https://ar5iv.labs.arxiv.org/html/2302.04761)).

For the existing REINFORCE loop with a result-check reward, the RL literature's consensus translates directly (inference on the mapping; each element sourced). Use 1[final number correct] as the base; add an efficiency term that is multiplicative and zero when the answer is wrong (OTC) or a per-call penalty applied only to unnecessary calls (Spurious Tool Use), never a flat per-call cost or a length reward, which collapsed ToolRL's irrelevance detection to 4.52% ([OTC §3](https://arxiv.org/abs/2504.14870); [Spurious Tool Use §4.1](https://arxiv.org/abs/2609.16268); [ToolRL Table 5](https://arxiv.org/abs/2504.13958)). The synthetic generator knows the true number of arithmetic steps, so the optimal call count n (0, 1 or 2) is known a priori, which OTC names as the case its sin-reward extends to without the group-minimum estimate ([OTC §3](https://arxiv.org/abs/2504.14870)). Apply the efficiency term only to correct rollouts and scale it down on problems the model mostly fails (AdaTIR, EAPO), because with few rollouts a penalty on correct one-call trajectories can make them lose to wrong zero-call ones (the "sign reversal" problem) ([AdaTIR](https://arxiv.org/abs/2601.14696); [EAPO](https://arxiv.org/abs/2606.02132)). Generate some rollouts with the `<calc>` logit forced off so zero-call solutions are in the comparison group (EAPO's 2 of 16) ([EAPO](https://arxiv.org/abs/2606.02132)). Keep any format reward binary (well-formed call block or not) and weighted below correctness, and change reward weights smoothly if at all ([Nemotron Tool-N1 Table 4](https://arxiv.org/abs/2505.00024); [ToolRL Table 6](https://arxiv.org/abs/2504.13958)). Expect spurious triggers to appear precisely once one-step calling is well learned, which is when the Spurious-Tool-Use mechanism says shortcuts form ([Spurious Tool Use §5.3](https://arxiv.org/abs/2609.16268)).

### Two-step chaining: train it explicitly and log the hand-off

Put explicit two-call traces in the supervised data from the start, in Calc-X's interleaved shape where the second call's operand is re-typed from the first call's result, and mix one-step and two-step problems; Toolformer's inability to chain is explained by its authors entirely by the absence of chained examples, and ToolkenGPT's one-hop-to-multi-hop transfer (0.15 versus 0.06) is real but too weak to rely on ([Toolformer §7](https://ar5iv.labs.arxiv.org/html/2302.04761); [ToolkenGPT Table 2](https://arxiv.org/abs/2305.11554); [Calc-X Fig. 2](https://ar5iv.labs.arxiv.org/html/2305.15017)). No source documents a one-step-to-two-step curriculum; ToRL's call cap is the only related knob, so a curriculum is an experiment, not a precedent (gap across sources). The hand-off between calls is where the errors will concentrate: with single-token numbers the digit-level copy error vanishes, but PoT's finding that 47% of failures are value-grounding errors says the which-number error remains, so the validator should record whether call 2's operand equals call 1's result and report that rate separately from final-answer accuracy ([PoT §3.4](https://arxiv.org/abs/2211.12588); metric is inference). Keep the second call within a few tokens of the first result, since attention dilutes with distance, and give each result its own marker so the second read is not a "most recent write" lookup (inference from [Liu et al.](https://arxiv.org/abs/2306.00946)). Magister's carry-forward correction is unnecessary when the result is overridden at generation time, but its motivation applies in reverse: the CPU cannot repair a wrong operand the model typed in call 2, so a mismatch between call 2's operand and call 1's result should be logged as a distinct failure class (inference from [Magister et al. §4](https://ar5iv.labs.arxiv.org/html/2212.08410)). For the REINFORCE stage, ToRA's prefix repair has a cheap synthetic analogue: when a sampled two-step trajectory fails after a correct first call, keep the prefix through that call and complete it with the generator's ground-truth continuation, which yields on-policy-looking two-step data without a teacher model ([ToRA §2.3](https://arxiv.org/abs/2309.17452); analogue is inference). Four layers is the low end for two verbalized steps plus a copy, per Ye et al.'s depth result and Wang et al.'s layer-split finding, so if chaining stalls, depth is the first architectural variable to test, and Olsson's smeared-key trick (a trainable mix of the current and previous token's key) is a near-free way to make previous-token information available without spending a head ([Ye et al.](https://arxiv.org/abs/2407.20311); [Wang et al.](https://arxiv.org/abs/2405.15071); [Olsson et al.](https://transformer-circuits.pub/2022/in-context-learning-and-induction-heads/index.html); application is inference).

### What to expect on unseen sentence shapes: surface triggers, a glitch tail, and seed variance

Expect the call decision to be a surface pattern over nearby story words rather than a general "I need to compute" judgement, for four converging reasons: Toolformer's models were "sensitive to the exact wording of their input when deciding whether or not to call an API" ([Toolformer §7](https://ar5iv.labs.arxiv.org/html/2302.04761)); Lee et al.'s mixed-corpus model swung from 84% to 97% to 88.7% accuracy depending on the exemplar preceding the problem ([Lee et al.](https://arxiv.org/abs/2307.03381)); outcome-trained agents bound calls to causally irrelevant cues within 30 RL steps ([Spurious Tool Use Table 1](https://arxiv.org/abs/2609.16268)); and small transformers store each hop of a composition in specific layers and reduce composition to "linearized pattern matching" ([Wang et al.](https://arxiv.org/abs/2405.15071)). The practical consequence (inference) is that templates which move or replace the cue words ("got 5 more" versus "found 5" versus "5 were given to him") will fail at a rate the in-distribution evaluation cannot reveal; no source tests paraphrase robustness of the call decision for arithmetic specifically, so this must be measured directly with held-out templates, and the mitigation with the most support is template and paraphrase diversity in the training generator. On the copy itself, expect in-distribution accuracy to reach the high 90s quickly and then leave a residual 0.1-few-percent tail of wrong-number copies that does not vanish with more of the same data and varies by seed, following Liu et al.'s flip-flop results; report error rates across at least three seeds, on held-out operand pairs, and separately for the "nearby distractor" (12, 5 and 17 within a few tokens) and "repeated value" (the result value already present earlier) cases ([Liu et al.](https://arxiv.org/abs/2306.00946); [Jelassi et al.](https://arxiv.org/abs/2402.01032); protocol is inference). Weight decay and longer training favour the generalizing circuit over the memorizing one in both Nanda's and Wang's settings, so a non-trivial weight decay is a cheap hedge ([Nanda et al.](https://arxiv.org/abs/2301.05217); [Wang et al.](https://arxiv.org/abs/2405.15071); application is inference). On data budget, 2,000-10,000 snippets at about 30 tokens each cost 0.06-0.3M of the 5M tokens, the same order as Lee et al.'s mixing ratios, and multiple epochs are the norm in every small-scale precedent (Saldyt's 62 epochs, Lee's thousands of iterations, Nanda's 10k epochs), so plan for several passes over the corpus rather than one (inference from [Lee et al.](https://arxiv.org/abs/2307.03381) and [Saldyt & Kambhampati](https://arxiv.org/abs/2407.04899)).

## Conclusion

The literature's clearest lesson is that a tool call is a data-format decision before it is a modelling decision: every successful system reduces to "stop on a delimiter, paste, resume", and the differences that matter are whether the pasted answer is a training target and whether the training text contains positions where not calling is the right move. Both of those are cheap to control in a synthetic story corpus, which is an advantage no surveyed paper had; the generator knows the true number of arithmetic steps, so the necessity label that Spurious Tool Use had to buy from an LLM judge, the optimal call count that OTC had to estimate from a rollout group, and the value-grounding error that PoT could only count by hand are all available exactly, per call, for free. The redesign should treat those three logs as first-class evaluation outputs rather than afterthoughts, because they are the only way to tell apart the three failure stories (did not call, called with the wrong numbers, called correctly and miscopied) that every larger-scale paper leaves confounded.

The open question that no source answers is whether a model this small learns the call decision as a reusable mechanism or as a lookup over story cue words, and the surrounding evidence (Toolformer's wording sensitivity, Lee's exemplar sensitivity, Wang's layer-bound hops) predicts the latter at four layers. That makes the held-out-template evaluation the real test of the redesign, not in-distribution accuracy, and it suggests the most informative ablation is depth, not data: if a 6- or 8-layer variant generalizes to moved cue words where the 4-layer one does not, the story GPT has found the same depth-for-composition trade-off that Ye et al. and Wang et al. report at 100M scale, in a model small enough to inspect head by head.
